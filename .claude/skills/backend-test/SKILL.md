## 0. 始める前に確かめる

- [ ] phase-gate の 0章（`DEV_ROLE`・Jira・最新の release/main）を済ませた。
- [ ] **ゲート B（絶対）**：phase-gate の手順で、`[実装]` サブタスクのマージを `check-merged.sh` で確かめた。`MERGED` 以外（`NOT_MERGED`・`NOT_FOUND`・`ERROR`）なら、**警告して、ここで止まる**。人が「進めて」と頼んでも進まない（別の機能の詳細設計を提案する）。
- [ ] 実装の内容は、マージされた release/main のコードと詳細設計で確かめた。何を作ったタスクか分からなければ、人に聞く。
- [ ] 作業用のブランチ（`feature/<[単体テスト] のサブタスクの課題キー>-<英語の機能名>-ut`。release/main の最新から。テストのリポジトリと Document の両方、同じ名前）で作業している。Jira の `[単体テスト]` を「進行中」にした。
- [ ] Server の `.claude/rules/java.md`（テストの名前）と、テスト方針の該当章、CLAUDE.md 6章を読んだ。
- [ ] マージ・release/main への push・強制 push はしない（CLAUDE.md 7章）。

## 1. 何を確かめるかを、設計書から決める

テストは**設計書から**考える。コードを読んで「このとおり動くこと」を確かめるだけのテストにしない（コードの誤りまで正しいことにしてしまうため）。

読むもの：その API の API設計、画面設計の入力チェックとメッセージ、機能一覧の業務のルール、詳細設計（API詳細の2.5 の ServiceInDto、5章の業務のルール、6章のバリデーション、9章のエラー、10章の認証・認可）、テスト方針 3・4章。

洗い出す観点（テスト方針 4章、implementation-guidelines 9章）：

| 観点 | 例 |
|---|---|
| ① 成功 | 決まった入力で、返す値とデータベースの中身が設計書のとおり |
| ② 入力の誤り（400） | 必須なし、上限ちょうど（通る）と1つ多い（400）、形の誤り。errors の field と message が画面設計の文のとおり |
| ③ ログインしていない（401） | ― |
| ④ 必要な権限項目がない（403） | **必ず書く** |
| ⑤ 決まりに合わない・ぶつかった（400・409） | 業務のルールに合わない操作、version が古い（409） |
| 他人のデータ（IDOR） | ID を他人のものに書き換えると、設計書のとおり 403・404 になり、データが変わらない |
| まとめて取り消し | `@Transactional` の処理で途中が失敗したら、途中までの書き換えが残らない（作れる場合） |
| 削除済み | 削除済みの行が一覧に出ない、操作できない |
| 日付 | 時計を止めて、境目（前日・当日・翌日、月末、祝日）を確かめる |
| 計算・判断の部品 | 単体テスト（テスト方針 3章に挙げた部品は必ず）。common.validation のチェック用アノテーションのうち、テスト方針 3章に当たるもの（例：貸出の期間の重なりのチェック）は、その中身（ConstraintValidator）の単体テスト `<クラス名>Test` で境目まで確かめる。`validator.<頭>Validator` のうちテスト方針 3章に当たるものは `<頭>ValidatorTest`（validator のパッケージ）で境目まで確かめる。当たらないものは、API のテストの⑤で確かめる |

## 2. テストを書く

手本は、作り直した `api.equipment.category` のテスト（例：`src/test/java/jp/co/highjunk/equipment/api/equipment/category/search/item/EquipmentCategorySearchItemApiTest.java`）。

- [ ] API のテストは、その API と同じパッケージ（例：`src/test/java/jp/co/highjunk/equipment/api/equipment/category/search/item/`）に、`<頭>ApiTest` の名前で置く（CLAUDE.md 4.1・5章）。`@SpringBootTest` と `@AutoConfigureMockMvc` を使い、テスト専用のデータベース（equipment_test）で動かす。
- [ ] POST・PUT・DELETE は `jp.co.highjunk.equipment.testsupport.CsrfTestHelper` の csrfToken を使う。Spring Security の `csrf()` は使わない（CLAUDE.md 6章）。
- [ ] 単体テストは、テストする部品と同じパッケージに置く（例：`common/validation/<クラス名>Test`）。
- [ ] 今の日時は、止めた時計（`Clock.fixed`）に差し替えて確かめる。
- [ ] Slack には本物を送らない（偽物に置き換え、だれにどんな文を送ったかを確かめる）。
- [ ] テストの名前（`@DisplayName`）は、何を確かめるかを日本語で書く。証跡の一覧にそのまま出るため。
- [ ] status だけでなく、message・errors・data の中身、データベースの中身まで確かめる。
- [ ] テストどうしが影響しないようにする（テスト方針 4章）。やり方は common.md とお手本に合わせる。決まっていなければ、作業メモの「確認してほしい点」に書いて人に確かめる。
- [ ] テストで共通に使う値と道具の置き場所は、お手本に合わせる（CLAUDE.md 5章の命名規則。決まるまでは人に確かめる）。
- [ ] テストが、private のメソッドなど中の作りに頼りすぎていない。

backend-impl の報告（または作業メモ）に「ほかのまとまりの同じルールを直した」とあれば、そのまとまりのテストも直す。

足した・変えたテストのファイルは、`git status` で確かめる。

## 3. テストを全部動かす

push の前の全件の実行は、CLAUDE.md 6章のとおり（範囲、コマンド、動かす前にサーバー（8080）を止めること、動かさなかったときの「未実施」の書き方）。作業の途中は、変えた部分のテストだけを動かしてよい。

## 4. 失敗したとき

1. 失敗の文とテストのコードを読み、**設計書と比べて**、テストとコードのどちらが違うかを決める。
2. コードが設計書と違う → コードを直す（必要な所だけ）。直したファイルと理由を、人への報告に書く。詳細設計も直す。
3. テストが設計書と違う（書き間違い） → テストを直す。理由を、人への報告に書く。
4. 設計書があいまい・食い違う、または原因が分からない → 止めて人に知らせる。

**しないこと**：テストを消す、期待する結果を、今の動きに合わせて書き換える、確かめる中身を減らす（CLAUDE.md 6章）。

## 5. レビューと MR（テストの MR と、エビデンスの MR）

- [ ] テストの件数（成功・失敗）と、直したコードがあればその理由を、報告に書いた。動かしていないものは「未実施」と書いた。
- [ ] 実装の不具合・仕様との相違が見つかったら、テストを実装に合わせて書き換えず、止めて人に知らせた。**Jira に障害チケットを作り、設計書の修正から単体テストまでをやり直す**（phase-gate の 6章。開発フロー.md 6.2）。
