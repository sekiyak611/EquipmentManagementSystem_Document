# 成果物の zip を作る

対象のタスク：$ARGUMENTS

（空なら、人にタスク名を聞く。）

決まりの正本は CLAUDE.md 6章・7章とテスト方針 7章。Git の作業は何もしない（状態を見るだけのコマンドも動かさない）。

## 作業記録の形

1つのタスクの作業記録は、Claude Code を起動したリポジトリ（Server か Client）の `output/<タスク名>/` に置く（CLAUDE.md 7章）。backend-impl・backend-test・frontend-impl・frontend-test が書きため、レビューと zip づくりが読む。output/ は Git で管理しない。

**タスク名の決め方**（作業記録のフォルダと zip の名前に使う。CLAUDE.md 7章）
- Document の `internaldesign/実装タスク一覧.md` の「タスク」の名前を使う（Jira の課題の名前から、頭の `[4.1]` のような番号を除いたもの。例：`種別管理`、`雛形：サーバー（backend）`）。
- Windows のファイル名に使えない半角の文字（`\ / : * ? " < > |`）と空白は除く（全角の「：」「（）」はそのまま使ってよい）。例：`Slack催促の定期実行`、`ログイン・ログアウト・権限の確かめ方`。
- Jira の課題キーしか分からないときは、人にタスク名を聞く。
- Jira のタスクにない作業（決まりの変更など）は、中身が分かる短い名前を人と決める（例：`パッケージ構成の変更`）。
- 課題キーは、作業メモ・変更ファイル一覧・説明.md の中に書く（名前には入れない）。

**output/<タスク名>/変更ファイル一覧.md**（zip にもこのまま入れる）

```
# 変更ファイル一覧（<課題キー> <タスク名>　YYYY-MM-DD）

## EquipmentManagementSystem_Server
| 区分 | ファイル |
|---|---|
| 足した | src/main/java/… |
| 変えた | … |
| **消した** | …（消すと空になるフォルダがあれば、それも書く） |

## EquipmentManagementSystem_Client
（変更がなければ「変更なし」）

## EquipmentManagementSystem_Document
| 区分 | ファイル |
|---|---|
| 変えた | internaldesign/詳細設計/… |
| 足した | evidence/<フォルダ名>/（フォルダごと。deliver-zip が足す） |
```

ファイルの場所は、リポジトリのいちばん上からの道のりで書く。

**output/<タスク名>/作業メモ.md**（zip には入れない。説明.md を書くもとにする）

```
# 作業メモ（<課題キー> <タスク名>）

## 進み具合
- [ ] backend-impl
- [ ] backend-test
- [ ] backend-review（指摘を直した）
- [ ] frontend-impl
- [ ] frontend-test
- [ ] frontend-review（指摘を直した）
- [ ] deliver-zip
（このタスクでしないものは「対象外」と書く）

## もとにした設計書
- …

## テストの結果（最後に動かしたもの）
- Server：○件中 成功○件・失敗○件（YYYY-MM-DD）
- Client：○件中 成功○件・失敗○件（YYYY-MM-DD）

## 確認してほしい点
- （判断に迷った所、設計書にない判断、足した Enum、ほかの機能の同じルールを直したこと、気づいた不具合、設計書を直したほうがよいと思った点）

## テストで見つかって直したこと
- …
```

## 1. 作業記録を読む

- [ ] `output/<タスク名>/作業メモ.md` で、このタスクの skill がすべて済んでいる（レビューの指摘も直してある）。済んでいなければ、人に知らせて確かめる。
- [ ] `output/<タスク名>/変更ファイル一覧.md` のファイルが、すべて実際にある（消したものは、ないこと）。
- 作業記録がないときは、人に、変えたファイルを聞く（Git では調べない）。

## 2. テストを全部動かして、成功を確かめる

Server・Client のどちらを変えても、両方動かす（CLAUDE.md 6章）。証跡は、この最後の結果から作る。

| どこで | コマンド |
|---|---|
| Server のフォルダ | `./gradlew test`（PowerShell なら `.\gradlew.bat test`） |
| Client のフォルダ | `npx playwright test`（その前に、開発用の設定で起動したサーバーを止めておく） |

1件でも失敗していたら、zip を作らない。テストを消したり、期待する結果を書き換えたりしない。人に知らせ、backend-test・frontend-test に戻る。

## 3. 証跡を残す

置き場所は Document の `evidence/<日付>_<テストの種類>_<内容>/`（テスト方針 7章）。日付は今日（例：20261210）。内容はタスクを短く（例：種別管理）。

| テスト | フォルダ名の例 | 写すもの |
|---|---|---|
| 単体・結合（API） | `20261210_単体結合API_種別管理` | Server の `build/reports/tests/test/` の中身 → `report/`、`build/test-results/test/` の中身 → `results/` |
| 結合（画面） | `20261210_結合画面_種別管理` | Client の `playwright-report/` の中身 → `report/`、`test-results/` の中の各テストの最後の画面 → `screenshots/`（ファイル名はテストのフォルダ名） |

それぞれのフォルダに `テスト結果.md` を書く。

```
# テスト結果（<課題キー> <タスク名>　Server 側／Client 側）

| 項目 | 内容 |
|---|---|
| 実施日 | YYYY-MM-DD |
| 実施者 | Claude Code（<だれのPCか>） |
| 実施した環境 | OS、Java（または Node.js・Playwright）、MySQL の版 |
| 動かしたコマンド | … |
| 結果 | ○件中 成功 ○件・失敗 0件 |
| 未実施 | （あれば） |

詳しいレポートは report/index.html。

## テストの一覧

### <テストのクラス・ファイル>（○件・失敗0件）
- （テストの名前。@DisplayName やテストの名前をそのまま）
```

件数は、レポートや結果のファイルから数える（覚えている数を書かない）。足した証跡のフォルダを、変更ファイル一覧.md の Document の表に書く。

## 4. zip に入れるものを集める

`output/<タスク名>_<日付>/` というフォルダを新しく作り、次の形に集める（CLAUDE.md 7章）。

```
output/種別管理_20261210/
├─ 説明.md
├─ 変更ファイル一覧.md                    （output/種別管理/ のものを写す）
├─ EquipmentManagementSystem_Server/ …   足したファイルと変えたファイル（リポジトリと同じフォルダの形）
├─ EquipmentManagementSystem_Client/ …   同じ
└─ EquipmentManagementSystem_Document/ … 書いた・直した詳細設計（internaldesign/詳細設計/）と、今回の証跡（evidence/）
```

- 変えていないリポジトリのフォルダは作らない。
- 消したファイルは入れず、変更ファイル一覧.md にだけ書く。
- 作業メモ.md は入れない。
- 入れてはいけないもの：`secret.yml`、`build/`、`.gradle/`、`node_modules/`、`dist/`、`logs/`、`bin/`、`.git/`、ほかのタスクの証跡。

**説明.md**（作業メモをもとに書く。人がプルリクエストを作るときに、そのまま使う。CLAUDE.md 7章の形）

```
## 目的
（Jiraの課題キーと、何のための変更か）
## 変更した内容
（主な変更を箇条書き）
## もとにした設計書
（例：docs/画面設計.md 3章、docs/API設計.md B-01）
## テストの結果
（動かしたテストの件数・成功・失敗。証跡の置き場所）
## とくに確認してほしい点
（作業メモの「確認してほしい点」と「テストで見つかって直したこと」。レビューで「確認したい」になった点）
```

## 5. zip にする

zip の名前は `<タスク名>_<日付>.zip`（例：種別管理_20261210.zip。タスク名の決め方は「作業記録の形」）。置き場所は `output/`。

JDK の jar の道具で作る（Java 21 に入っているので、どのPCにもある）。リポジトリのいちばん上で：

```
jar --create --no-manifest --file output/種別管理_20261210.zip -C output/種別管理_20261210 .
```

できたら、中身を一覧にして確かめる。

```
jar --list --file output/種別管理_20261210.zip
```

- [ ] 日本語のファイル名（説明.md、詳細設計 など）が正しく出る。文字化けしたり、エラーになったりしたら、PowerShell で作り直す：`powershell -NoProfile -Command "Compress-Archive -Path 'output/種別管理_20261210/*' -DestinationPath 'output/種別管理_20261210.zip' -Force"`
- [ ] いちばん上に 説明.md・変更ファイル一覧.md と、リポジトリの名前のフォルダがある。
- [ ] 入れてはいけないもの（4の一覧）が入っていない。とくに `secret.yml` と、`xoxb-` で始まる文字（Slack のトークン）がない。

作業メモの進み具合で「deliver-zip」に印を付ける。`output/<タスク名>/` は消さない（あとで直すときに使う）。

## 6. 人に渡す

人に、zip の場所（例：`output/種別管理_20261210.zip`）と、説明.md の「とくに確認してほしい点」を短く伝える。消したファイルがあれば、人が自分でリポジトリから消す必要があることも伝える。ブランチ・コミット・プルリクエストは人が行う。
