# 仕上げ：テスト → 証跡 → commit・push → プルリクエスト

対象のタスク：$ARGUMENTS

（空なら、人にタスク名と Jira の課題キーを聞く。）

決まりの正本は CLAUDE.md 6・7・10章、`決まり/Git運用.md`（ブランチ・commit・プルリクエストの形、してよいこと・いけないこと）、テスト方針 7章。この skill は手順だけを書く。マージ・release/main への push・強制 push は、しない（人が行う）。

**タスク名**：実装タスク一覧.md の「タスク」の名前（例：`種別管理`）を、証跡のフォルダ名とプルリクエストの名前に使う。Windows のファイル名に使えない文字（`\ / : * ? " < > |`）と半角の空白は除く。Jira にない作業は、中身が分かる短い名前を人と決める。

## 1. 始める前に確かめる

- [ ] 変えたリポジトリ（Server・Client・Document）のすべてで、ブランチが `feature/<課題キー>-<英語の機能名>`（release/main から。3つとも同じ名前）。
- [ ] `git status` で、変えたファイルが、このタスクの対象だけ（対象の外の変更がない）。`secret.yml`・`.env`・`build/`・`node_modules/` などが入っていない。
- [ ] 実装・テスト・レビューの skill が済み、レビューの指摘を直した（直さなかったものは、理由が分かる）。

## 2. テストを全部動かして、成功を確かめる

Server・Client のどちらを変えても、両方動かす（CLAUDE.md 6章）。証跡は、この最後の結果から作る。

| どこで | コマンド |
|---|---|
| Server のフォルダ | `.\gradlew.bat test --rerun` |
| Client のフォルダ | `npx playwright test`（その前に、Eclipse で動かしているサーバー（8080）を止める。MySQL は動かしておく） |

1件でも失敗していたら、commit・push・プルリクエストに進まない。テストを消したり、期待する結果を書き換えたりしない。人に知らせ、backend-test・frontend-test に戻る。件数は、結果のファイルから数える（覚えている数を書かない）。

## 3. 証跡を残す

置き場所は Document の `evidence/<日付>_<テストの種類>_<内容>/`（テスト方針 7章）。日付は今日（例：20261210）。

| テスト | フォルダ名の例 | 写すもの |
|---|---|---|
| 単体（部品・API） | `20261210_単体API_種別管理` | Server の `build/reports/tests/test/` の中身 → `report/`、`build/test-results/test/` の中身 → `results/` |
| 単体（画面） | `20261210_単体画面_種別管理` | Client の `playwright-report/` の中身 → `report/`、`test-results/` の各テストの最後の画面 → `screenshots/`（ファイル名はテストのフォルダ名） |

それぞれのフォルダに `テスト結果.md` を書く。

```
# テスト結果（<課題キー> <タスク名>　Server 側／Client 側）

| 項目 | 内容 |
|---|---|
| 実施日 | YYYY-MM-DD |
| 実施者 | Claude Code（<だれのPCか>） |
| 実施した環境 | OS、Java（または Node.js・Playwright）、MySQL の版 |
| 動かしたコマンド | … |
| 結果 | ○件中 成功 ○件・失敗 0件 |
| 未実施 | （動かしていないテスト、確かめていないこと。なければ「なし」） |

確かめたこと：（設計書の章と対応づけて、箇条書き）

## テストの一覧
### <テストのクラス・ファイル>（○件・失敗0件）
- （@DisplayName やテストの名前をそのまま）
```

- Windows のパスの長さの制限で、`$Race` などの長い名前のレポートのフォルダは、git に入れられないことがある。その場合は、プルリクエストの説明に書く（results は全部ある）。
- ほかのタスクの証跡を入れない。

## 4. 完成条件を確かめる（CLAUDE.md 10章）

CLAUDE.md 10章の完成条件を、1つずつ確かめる。欠けているものは、完了と言わず、プルリクエストの「未実施・未確認・対象外」に書く。

## 5. commit・push

変えたリポジトリごとに、作業の区切り（実装・テスト・詳細設計など）で commit を分ける。1行目は `<課題キー> <タスク名>：何をしたか`（日本語）。末尾に、システムの指示にある共同作成者の行を付ける。`git push -u origin feature/<課題キー>-<英語の機能名>`。

## 6. プルリクエストを作る

変えたリポジトリごとに作る。名前は `<課題キー> <タスク名>：…`。説明は `決まり/Git運用.md` の形（目的／変更した内容／もとにした設計書／テストの結果／**未実施・未確認・対象外**／とくに確認してほしい点／関係するプルリクエスト）。末尾に、システムの指示にある生成の行を付ける。

- `gh` が使えなければ、ブラウザで `https://github.com/<オーナー>/<リポジトリ>/compare/release/main...<ブランチ名>?expand=1` を開き、説明を入れて作る。ログインはしない（人にしてもらう）。
- Document のプルリクエストに、詳細設計と証跡を入れる。ほかのリポジトリの番号を「関係するプルリクエスト」に書く。

## 7. 人に報告する

プルリクエストの場所、「とくに確認してほしい点」、未実施・未確認のことを短く伝える。取り込み（マージ）は人が行う。
