# 仕上げ：工程の MR を出す

対象：$ARGUMENTS（最初の言葉が工程。空なら、人に工程とタスク名を聞く。）

決まりの正本は CLAUDE.md 6・7・10・11章、`決まり/開発フロー.md`、`決まり/Git運用.md`、テスト方針 7章。この skill は手順だけを書く。マージ・release/main への push・強制 push は、しない（リーダーが行う）。

## 1. 始める前に確かめる

- [ ] 工程（design・impl・ut）と、そのサブタスクの課題キーが分かっている（phase-gate の 0章）。
- [ ] 変えたリポジトリのすべてで、ブランチが `feature/<サブタスクの課題キー>-<英語の機能名>-<design|impl|ut>`（release/main から。同じ工程では、同じ名前）。
- [ ] `git status`・`git diff` で、変えたファイルが、**この工程の成果物だけ**。
  - design：詳細設計（Document）だけ。実装・テスト・エビデンスを入れない。
  - impl：コード（Server か Client）だけ。詳細設計を直さない（直すなら、設計の修正の MR（開発フロー.md 6.1）を先に出す）。
  - ut：テストのコード（Server か Client）と、エビデンス（Document）だけ。実装のコードを直さない（不具合なら、障害チケットを作ってやり直す（開発フロー.md 6.2））。
  - `secret.yml`・`.env`・`build/`・`node_modules/` などが入っていない。
- [ ] 独立した AI レビューの指摘を直し、人のチェックが済んでいる。人が手で直した所は、`git diff` で読んで反映した。

## 2. テストを動かす

| 工程 | 動かすもの |
|---|---|
| design | 動かさない（ドキュメントだけ） |
| impl | Server・Client の**すでにあるテストを全部**（壊れていないかの確認。ArchitectureTest を含む）。新しい機能のテストは、書かない（次の工程） |
| ut | Server・Client の**テストを全部**。証跡は、この最後の結果から作る |

| どこで | コマンド |
|---|---|
| Server のフォルダ | `.\gradlew.bat test --rerun` |
| Client のフォルダ | `npx playwright test`（その前に、Eclipse で動かしているサーバー（8080）を止める。MySQL は動かしておく） |

1件でも失敗していたら、commit・push・MR に進まない。テストを消したり、期待する結果を書き換えたりしない。人に知らせる。件数は、結果のファイルから数える（覚えている数を書かない）。

## 3. 証跡を残す（ut のみ）

置き場所は Document の `evidence/<日付>_<テストの種類>_<内容>/`（テスト方針 7章）。日付は今日（例：20261210）。

| テスト | フォルダ名の例 | 写すもの |
|---|---|---|
| 単体（部品・API） | `20261210_単体API_種別管理` | Server の `build/reports/tests/test/` の中身 → `report/`、`build/test-results/test/` の中身 → `results/` |
| 単体（画面） | `20261210_単体画面_種別管理` | Client の `playwright-report/` の中身 → `report/`、`test-results/` の各テストの最後の画面 → `screenshots/`（ファイル名はテストのフォルダ名） |

それぞれのフォルダに `テスト結果.md` を書く。

```
# テスト結果（<課題キー> <タスク名>　Server 側／Client 側）

| 項目 | 内容 |
|---|---|
| 実施日 | YYYY-MM-DD |
| 実施者 | Claude Code（<だれのPCか>） |
| 実施した環境 | OS、Java（または Node.js・Playwright）、MySQL の版 |
| 動かしたコマンド | … |
| 結果 | ○件中 成功 ○件・失敗 0件 |
| 未実施 | （動かしていないテスト、確かめていないこと。なければ「なし」） |

## 確かめたこと（根拠）
| 観点 | 根拠（設計書の章） | テスト |
|---|---|---|
| （例）必須項目が空なら 400 | 画面設計 3章、API設計 2.4 | XxxApiTest の「必須…」 |

（期待する結果の根拠は、実装ではなく、設計書。根拠がなく推測で決めた観点は、「推測」と書く）

## テストの一覧
### <テストのクラス・ファイル>（○件・失敗0件）
- （@DisplayName やテストの名前をそのまま）
```

- Windows のパスの長さの制限で、`$Race` などの長い名前のレポートのフォルダは、git に入れられないことがある。その場合は、MR の説明に書く（results は全部ある）。
- ほかのタスクの証跡を入れない。

## 4. 完成条件を確かめる（CLAUDE.md 10章）

1つずつ確かめる。欠けているものは、完了と言わず、MR の「未実施・未確認・対象外」に書く。

## 5. commit・push

変えたリポジトリごとに、作業の区切りで commit を分ける。1行目は `<サブタスクの課題キー> <タスク名>：何をしたか`（日本語）。末尾に、システムの指示にある共同作成者の行を付ける。`git push -u origin feature/<サブタスクの課題キー>-<英語の機能名>-<design|impl|ut>`。

## 6. MR を作る

変えたリポジトリごとに作る（design＝Document。impl＝Server か Client。ut＝Server か Client と、Document の2つ）。

- 名前：`<サブタスクの課題キー> [詳細設計|実装|単体テスト] <タスク名>：…`。説明は `決まり/Git運用.md` の形（目的／変更した内容／もとにした設計書／テストの結果／**未実施・未確認・対象外**／とくに確認してほしい点／関係する MR）。末尾に、システムの指示にある生成の行を付ける。
- **`DEV_ROLE=junior` の人は、Draft（下書き）で作る。** 経験者かリーダーのレビューが済んだら Ready にする。`senior`・`leader` は Ready で作る。
- ut の2つの MR は、「関係する MR」で互いを指す。
- `gh` が使えなければ、ブラウザで `https://github.com/<オーナー>/<リポジトリ>/compare/release/main...<ブランチ名>?expand=1` を開き、説明を入れて作る。ログインはしない（人にしてもらう）。
- impl の MR を、設計が未マージのまま出すとき（ゲート A）は、Draft にして、説明に「先に Document の #番号 を取り込む」と書く。

作ったら、phase-gate の `mr-created`（Jira のサブタスクを「確認中」にする）を行う。

## 7. 人に報告する

MR の場所、「とくに確認してほしい点」、未実施・未確認のこと、次の流れ（レビュー → リーダーがマージ → 「マージした」と伝える）を短く伝える。マージ待ちのあいだ、別の機能の詳細設計を提案する（phase-gate の 5章）。
