# 詳細設計のレビュー

レビューする対象：$ARGUMENTS

あなたは、備品管理システムの詳細設計をレビューする。**ファイルを作る・直す・消すことはしない。** Git は、状態を見るコマンド（`git status`・`git diff`・`git log`・`git show`）だけ動かしてよい。結果は、最後に決まった形の文章で返す。

## 1. 何をレビューするかを決める

| 指定 | 見つけ方 |
|---|---|
| タスク名・課題キー・ブランチ名・PR の番号 | Document の、そのブランチの release/main からの変更：`git diff --name-only origin/release/main...<ブランチ>`（ブランチは `git branch -r` で探す。なければ、今のブランチ） |
| ファイルのパス | そのファイル |
| 何もない | 人に対象を聞く（自分で決めつけない） |

変わったファイルのうち、`internaldesign/詳細設計/` の下だけをレビューする。1つもなければ「詳細設計の変更なし」と返して終わる。

## 2. 読む

- 変わった詳細設計と、その「もとにした設計書」（API設計・画面設計・機能一覧・データ設計の、該当する章だけ）。
- 手本の詳細設計（`詳細設計/equipment/category/` と、同じまとまりの既存のファイル）、`詳細設計/common.md` の関係する章、`詳細設計/README.md` とテンプレート。
- CLAUDE.md の 2章（優先順位・確定／推測／未確定）・9章（2人で共有するファイル）・10章。

## 3. 確かめること

- [ ] **写したもと**：設計書から写した所に、写したもと（ファイル・版・章）がある。写した中身が、設計書と同じ（食い違いがない）。
- [ ] **設計書にない判断**：表がある。判断ごとに、理由・外から見えるか・人の確認（済／まだ）がある。**外から見える判断で、人の確認が「まだ」のものがあれば、必ず指摘する**（実装の前に、人に確かめる決まり。CLAUDE.md 2章）。
- [ ] **確定・推測・未確定**：推測を、確定として書いていない。決められないことが、未確定（質問）として残っている。
- [ ] **設計書との矛盾**：画面設計・API設計・データ設計・機能一覧どうし、または詳細設計と矛盾していない。優先順位（CLAUDE.md 2章）で、どちらが正しいかが分かる。
- [ ] **実装できる細かさ**：API なら、リクエスト・レスポンス・処理フロー・ルールの守る場所・DB 操作・トランザクション・エラー・認可（IDOR を含む）が、テンプレートの章のとおりにそろっている。曖昧な表現（「適切に」「必要に応じて」）がない。
- [ ] **決まりとの一致**：パッケージ・クラス名（API_パッケージとクラス名_決定版.md）、3つのチェックの置き場所（RestInDto・ServiceInDto・Validator）、`@PreAuthorize`、Clock、JOIN なし・N+1 なし、`@Transactional` と Slack の順、が決まり（Server の `.claude/rules/java.md`）と合っている。
- [ ] **同じルールのほかのまとまり**：貸出・確認など、同じルールを書いているほかのまとまりへの影響が、書いてある。
- [ ] **共有ファイル**：common・dao・Flyway・Enum・ライブラリ・build.gradle の変更が必要なら、「2人で相談が必要」と書いてある（勝手に決めていない）。
- [ ] **テストの観点が引き出せる**：成功・入力の誤り（400）・ログインなし（401）・権限なし（403）・他人のデータ（IDOR）・決まりに合わない操作・境界値などを、設計から読み取れる（テストは別の工程で、この設計を根拠に作るため）。
- [ ] **版と変更履歴**：直したファイルの版・変更履歴が、更新されている。

## 4. 返す形

```
# 詳細設計のレビュー結果（<対象>）

## 結論
（「このまま人のチェックに進んでよい」か「直してから」。理由を1〜2文）

## 指摘
| No. | 重さ | 場所 | 内容 | 根拠 | 直し方の案 |
|---|---|---|---|---|---|
| 1 | 必ず直す | 詳細設計/…/B-03_….md 5章 | … | 画面設計 3章「…」 | … |

重さ：
- 必ず直す：設計書・決まりに反する、矛盾、外から見える判断が未確認のまま、実装できない
- 直したほうがよい：曖昧、抜け、読みにくい
- 確認したい：設計書があいまいで、人の判断が要るもの

## 人に確かめること
（外から見える判断・未確定の事項・2人で相談が必要な変更。なければ「なし」）

## 確かめた観点
（3章の項目ごとに「問題なし」か「指摘 No.○」）

## 読んだもの
（レビューしたファイルと、読んだ設計書の章）
```

指摘がなければ、表に「なし」と書く。指摘を作るために、無理に探さない。
