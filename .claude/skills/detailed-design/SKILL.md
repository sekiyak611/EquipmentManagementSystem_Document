# 詳細設計を書く

対象：$ARGUMENTS

（空なら、人にまとまり（または API・画面の ID）と Jira の課題キーを聞く。）

書き方の正本は Document の `internaldesign/詳細設計/README.md`、形の正本は `internaldesign/詳細設計/テンプレート/` の3つ（機能.md・API.md・画面.md）。この skill には順番とチェック表だけを書く。

**詳細設計で設計書の決まりを変えない**（CLAUDE.md 2章）。設計書と違う作りが要るときは、書いて済ませずに人に質問する。

## 0. 詳細設計の工程（`決まり/開発フロー.md` ①）

この工程は、**詳細設計だけ**を作り、Document の MR を出す。実装・テストは、この MR がマージされたあと、別の工程で行う。

- [ ] phase-gate の 0章（`DEV_ROLE`・Jira・最新の release/main）を済ませた。先にやるタスクの `[詳細設計]` が完了しているかも見た。Jira の `[詳細設計]` を「進行中」にした。
- [ ] 作業用のブランチ（Document。`feature/<[詳細設計] のサブタスクの課題キー>-<英語の機能名>-design`。release/main の最新から）で作業している。
- [ ] 外から見える判断や、設計書のあいまいな所・食い違いがあれば、書き始める前に、spec-check の形で整理して、まとめて人に質問した。
- 書き終えたら：①独立した AI レビュー（`/design-review`。指摘は直す）→ ②人がチェック（直しは AI に頼むか手で直す。手で直したら `git diff` を読んで反映）→ ③`/deliver design`（commit・push・MR。`DEV_ROLE=junior` は Draft）→ ④リーダーがマージ → 人が「マージした」と伝える（phase-gate の merged）→ ⑤実装の工程へ（ゲート A）、または別の機能の詳細設計。

## 1. 何を書くかを決める

1. 対象のまとまりを決める（CLAUDE.md 4.1 の表の1行。例：api.equipment.category）。API の ID が渡されたら、`internaldesign/パッケージ構成変更/API_パッケージとクラス名_決定版.md` で、その API のパッケージとまとまりを探す。画面の ID が渡されたら、CLAUDE.md 4.3 の features の表で探す。
2. 書くファイルを決める。

| ファイル | 置き場所 | テンプレート | いつ書くか |
|---|---|---|---|
| まとまり全体 | `internaldesign/詳細設計/<まとまりのフォルダ>/<まとまりの名前>.md`（例：`equipment/category/category.md`） | テンプレート/機能.md | そのまとまりで最初に書くとき。API・画面を足したら書き足す |
| API詳細 | `internaldesign/詳細設計/<まとまりのフォルダ>/<APIのID>_<短い名前>.md` | テンプレート/API.md | タスクで作る・直す API ごとに1つ |
| 画面詳細 | `internaldesign/詳細設計/<まとまりのフォルダ>/<画面のID>_<短い名前>.md` | テンプレート/画面.md | タスクで作る・直す画面ごとに1つ |

- `<まとまりのフォルダ>` は、パッケージの `api` より後ろを入れ子のフォルダにしたもの（例：api.equipment.category → `equipment/category/`。README 2章）。

- 短い名前は、API設計 3章の「内容」・画面一覧の画面の名前を短くしたもの（例：`K-01_種別一覧.md`、`S-13_種別管理.md`）。
- 共通部品（common）は、テンプレートではなく common.md に章を足す。
- すでにファイルがあれば、新しく作らずに書き足す（版を上げ、変更履歴に書く）。

## 3. 質問を先に出す

読みながら、次のものを書き出す。1つでもあれば、**書き進める前に人に質問する**（推測で埋めない）。

- 設計書どうしの食い違い（例：画面設計の入力の上限と、データ設計の列の長さが違う）
- 設計書に書いていない、外から見える動き（返す値の項目、エラー、メッセージ、画面の移り方）。とくに、API設計 4章に例がない API の、受け取る値・返す値の項目
- 画面設計にない文が要りそうな所（例：0件のときに何か文を出すか）
- まとまりをまたぐ変更が要るもの（common の部品（common.validation のチェック用アノテーションを足すのを含む）、Flyway のファイル、dao の作り直し、すでにある Enum、ほかのまとまりの同じルール）

質問には「どの設計書の何章か」「何が分からないか、何が食い違うか」「考えられる案（あれば、おすすめ）」を書く。

## 4. 書く

テンプレートをコピーして、上から順に埋める。

**設計書から写す所**（README 3章）
- [ ] 写した所に「写したもと：ファイル名 版 章」を書いた。版は設計書の表の頭にある版。
- [ ] 画面の文・メッセージ・表示名・Slack の文を、一字も変えずに写した。
- [ ] 設計書の行や値を変えていない（列を足すのはよい）。
- [ ] 写した所に、自分で決めたことを混ぜていない（決めたことは「設計書にない判断」へ）。

**中の作りを書く所**

| ファイル・章 | 確かめること |
|---|---|
| まとまり全体 2章（クラス・ファイル構成） | CLAUDE.md 4.1・4.3 の置き場所と、5章の命名規則どおりの名前（`<頭>` は決定版のとおり）。使う dao の Mapper・Example、手で書く Mapper（あれば理由も）、足す・使うチェック用アノテーション（common.validation）、足す Enum、使う共通部品 |
| まとまり全体 3章（ほかのまとまりへの影響） | 同じルールを書いているまとまり（貸出：equipment.mine・equipment.management（取込を含む）、確認：equipment.mine・equipment.management）、同じテーブルを書き換えるまとまり |
| API詳細 2・3章（リクエスト・レスポンス） | RestInDto・RestOutDto の項目名・型・必須・制約。返す項目が、どのテーブルの列か計算か。パスワードのハッシュなど、返してはいけない項目を返していない |
| API詳細 2.5（ServiceInDto） | Controller が何から作るか（RestInDto の項目・パスの値・ログインしている人）、付けるチェック用アノテーション。受け取る値がなければ「なし」 |
| API詳細 4章（処理フロー） | 受け取る → 形式のチェック（RestInDto）→ 権限 → ServiceInDto を作る（Controller）→ DB との整合性のチェック（ServiceImpl の `@Transactional` の中で ServiceInDto を確かめる）→ 書き換え → 返す（RestOutDto）。順番が大事なものは Mermaid の図も |
| API詳細 5章（業務のルール） | ルールごとに、守る場所（受け取った値だけで DB と照らせば確かめられるものは ServiceInDto のチェック用アノテーション、ServiceImpl が読んだ・計算した値が要るものは `<頭>Validator`、値を作る・書き換えるものは `<頭>ServiceImpl`）と、守れないときのエラー |
| API詳細 6章（バリデーション） | RestInDto の印で確かめるもの（形式のチェック）、ServiceInDto のチェック用アノテーションで確かめるもの（DB との整合性と Enum。重複など）、Validator で確かめるもの（業務チェック。ValidatorDto に何を入れるかも） |
| API詳細 7章（DB操作） | dao の Mapper のメソッドと Criteria の条件、JOIN・サブクエリを使わない読み方、`andIdIn` でまとめて読む所、削除済みを除く条件、更新が0件のときの扱い、手で書く Mapper を使うならその SQL と理由 |
| API詳細 8章（トランザクション・排他） | 2つ以上の書き換えなら `@Transactional`、編集なら version、Slack は書き込みの確定後（CLAUDE.md 5章） |
| API詳細 10章（認証・認可） | 権限項目と、ID を受け取るならその人が操作してよい対象かの確かめ方（IDOR。ServiceInDto のチェックで確かめる） |
| 画面詳細 2.2・3章（部品・項目） | 項目ごとに MUI の部品、状態の名前、API の項目、表示の形 |
| 画面詳細 5・7章（操作・API） | 押したときの順番、処理中に押せなくする、呼ぶ API と関数の名前 |
| 画面詳細 6章（状態） | 読み込み中・0件・失敗・権限なしのときの表示。画面設計にない表示は文のないものだけ |
| 画面詳細 9章（メッセージ・エラー） | 完了・確認の文と、status ごとの出し方 |
| 各ファイルの「設計書にない判断」 | 自分で決めたことと理由。「外から見えるか」が「はい」のものは、実装の前に人に確かめる |

**書き方**
- 当てはまらない章は、消さずに「なし」と書く。テンプレートの `<!-- … -->` は消す。
- 専門用語は、初めて出てくる所で短く説明する。
- クラス名・メソッド名・テーブル名・列名は、コードと同じ文字で書く。
- まとまり全体の 1.1・1.2 の表から、API詳細・画面詳細のファイルへリンクする。

## 5. 実装のあとで突き合わせる

この確かめは、実装の工程の最後（backend-impl・frontend-impl の5章）で行う。食い違いがあれば、コードを直すか、設計の修正の MR を先に出す（実装の MR で詳細設計を直さない。開発フロー.md 6章の6.1）。次を1つずつ確かめる。

- [ ] まとまり全体 2章のクラス・ファイルが、すべてある。書いていないクラス・ファイルがない。
- [ ] API詳細 7章の Mapper のメソッドと Criteria の条件が、コードと同じ。手で書く Mapper があれば、その XML の SQL も同じ。
- [ ] API詳細 2.5 の ServiceInDto の項目とチェック用アノテーションが、コードと同じ。
- [ ] API詳細 6・9章、画面詳細 4・9章の文と、コードの文が同じ。
- [ ] 版を上げ、変更履歴に書いた。

## 6. 設計書が直ったとき

設計書が直ったと人から聞いたら、直った章を「写したもと」に書いているファイルを Document の中で探し（例：`画面設計.md v1.1 の16章` で検索）、写した所と版を直す。中の作りまで変わるなら、人に知らせて、別の作業（backend-impl・frontend-impl）にする。

画面設計.md・データ設計.md などの設計書そのものは、自分で直さない（CLAUDE.md 2章）。

この工程の MR は、詳細設計だけ（Document）。実装・テスト・エビデンスは入れない（CLAUDE.md 11章）。
