# 詳細設計を書く

対象：$ARGUMENTS

（空なら、人に機能名と Jira の課題キーを聞く。）

書き方の正本は Document の `internaldesign/詳細設計/README.md`、形の正本は `internaldesign/詳細設計/テンプレート/` の3つ（機能.md・API.md・画面.md）。この skill には順番とチェック表だけを書く。

**詳細設計で設計書の決まりを変えない**（CLAUDE.md 2章）。設計書と違う作りが要るときは、書いて済ませずに人に質問する。

## 1. 何を書くかを決める

1. 対象の機能を決める（CLAUDE.md 4.1 のパッケージの名前）。API・画面の ID が渡されたら、API設計 3章・画面一覧 2章から、その ID の機能を探す。
2. 書くファイルを決める。

| ファイル | 置き場所 | テンプレート | いつ書くか |
|---|---|---|---|
| 機能全体 | `internaldesign/詳細設計/<機能名>/<機能名>.md` | テンプレート/機能.md | その機能で最初に書くとき。API・画面を足したら書き足す |
| API詳細 | `internaldesign/詳細設計/<機能名>/<APIのID>_<短い名前>.md` | テンプレート/API.md | タスクで作る・直す API ごとに1つ |
| 画面詳細 | `internaldesign/詳細設計/<機能名>/<画面のID>_<短い名前>.md` | テンプレート/画面.md | タスクで作る・直す画面ごとに1つ |

- 短い名前は、API設計 3章の「内容」・画面一覧の画面の名前を短くしたもの（例：`K-01_種別一覧.md`、`S-13_種別管理.md`）。
- 共通部品（common）は、テンプレートではなく common.md に章を足す。
- すでにファイルがあれば、新しく作らずに書き足す（版を上げ、変更履歴に書く）。

## 2. 読む

- [ ] `internaldesign/詳細設計/README.md`（とくに3章「設計書の中身を写すときの決まり」と6章「どの機能でも同じこと」）
- [ ] テンプレート（書くファイルの分）
- [ ] お手本：`internaldesign/詳細設計/category/`（まだなければ `health/`）
- [ ] `internaldesign/詳細設計/common.md`（使える共通部品。ここにある部品を、機能の中に作り直さない）
- [ ] この機能のフォルダ（あれば。書き足すときは、今の版と変更履歴を見る）
- [ ] 設計書の、関係する章をすべて：

| 設計書 | 見る所 | 写す先 |
|---|---|---|
| externaldesign/機能一覧.md | この機能の F-xx、4章の共通ルール、5章以降の業務のルール | 機能全体 1章 |
| internaldesign/API設計.md | 2章（共通の決まり）、3章のこの機能の表、4章の例、6章（設定値）、7章（ログ） | 機能全体 1.1、API詳細 1〜3・9章 |
| externaldesign/画面一覧.md | 2章（画面）、4章（遷移図）、7章（スマートフォン） | 機能全体 1.2、画面詳細 1・8章 |
| externaldesign/画面設計.md | 1章（全画面の共通）、その画面の章（絵・項目・入力チェック・メッセージ・ボタン）、9章（Slack の文） | 画面詳細 2〜6・9章、API詳細 6・11章 |
| externaldesign/データ設計.md | 2章（共通の決まり）、使うテーブル、5.3（権限項目） | API詳細 7・10章 |
| internaldesign/CLAUDE.md | 4.1・4.3（置き場所）、5章（書き方の決まりと命名規則） | 機能全体 2章、API詳細 7・8・10章 |

## 3. 質問を先に出す

読みながら、次のものを書き出す。1つでもあれば、**書き進める前に人に質問する**（推測で埋めない）。

- 設計書どうしの食い違い（例：画面設計の入力の上限と、データ設計の列の長さが違う）
- 設計書に書いていない、外から見える動き（返す値の項目、エラー、メッセージ、画面の移り方）。とくに、API設計 4章に例がない API の、受け取る値・返す値の項目
- 画面設計にない文が要りそうな所（例：0件のときに何か文を出すか）
- 機能をまたぐ変更が要るもの（common の部品、Flyway のファイル、すでにある Enum、ほかの機能の同じルール）

質問には「どの設計書の何章か」「何が分からないか、何が食い違うか」「考えられる案（あれば、おすすめ）」を書く。

## 4. 書く

テンプレートをコピーして、上から順に埋める。

**設計書から写す所**（README 3章）
- [ ] 写した所に「写したもと：ファイル名 版 章」を書いた。版は設計書の表の頭にある版。
- [ ] 画面の文・メッセージ・表示名・Slack の文を、一字も変えずに写した。
- [ ] 設計書の行や値を変えていない（列を足すのはよい）。
- [ ] 写した所に、自分で決めたことを混ぜていない（決めたことは「設計書にない判断」へ）。

**中の作りを書く所**

| ファイル・章 | 確かめること |
|---|---|
| 機能全体 2章（クラス・ファイル構成） | CLAUDE.md 4.1・4.3 の置き場所と、5章の命名規則どおりの名前。足す Enum。使う共通部品 |
| 機能全体 3章（ほかの機能への影響） | 同じルールを書いている機能（貸出：mine・equipment・importer、確認：mine・equipment・confirmation）、同じテーブルを書き換える機能 |
| API詳細 2・3章（リクエスト・レスポンス） | 項目名・型・必須・制約。返す項目が、どのテーブルの列か計算か。パスワードのハッシュなど、返してはいけない項目を返していない |
| API詳細 4章（処理フロー） | 受け取る → 入力チェック → 権限 → 業務チェック（ServiceImpl から Validator）→ 書き換え → 返す。順番が大事なものは Mermaid の図も |
| API詳細 5章（業務のルール） | ルールごとに、守る場所（クラス.メソッド。確かめて止めるものは XxxValidator、値を作る・書き換えるものは XxxServiceImpl）と、守れないときのエラー |
| API詳細 6章（バリデーション） | dto の印で確かめるもの（入力チェック）、Validator で確かめるもの（業務チェック。重複など） |
| API詳細 7章（DB操作） | JOIN・サブクエリを使わない読み方、`IN` でまとめて読む所、削除済みを除く条件、更新が0件のときの扱い |
| API詳細 8章（トランザクション・排他） | 2つ以上の書き換えなら `@Transactional`、編集なら version、Slack は書き込みの確定後（CLAUDE.md 5章） |
| API詳細 10章（認証・認可） | 権限項目と、ID を受け取るならその人が操作してよい対象かの確かめ方（IDOR） |
| 画面詳細 2.2・3章（部品・項目） | 項目ごとに MUI の部品、状態の名前、API の項目、表示の形 |
| 画面詳細 5・7章（操作・API） | 押したときの順番、処理中に押せなくする、呼ぶ API と関数の名前 |
| 画面詳細 6章（状態） | 読み込み中・0件・失敗・権限なしのときの表示。画面設計にない表示は文のないものだけ |
| 画面詳細 9章（メッセージ・エラー） | 完了・確認の文と、status ごとの出し方 |
| 各ファイルの「設計書にない判断」 | 自分で決めたことと理由。「外から見えるか」が「はい」のものは、実装の前に人に確かめる |

**書き方**
- 当てはまらない章は、消さずに「なし」と書く。テンプレートの `<!-- … -->` は消す。
- 専門用語は、初めて出てくる所で短く説明する。
- クラス名・メソッド名・テーブル名・列名は、コードと同じ文字で書く。
- 機能全体の 1.1・1.2 の表から、API詳細・画面詳細のファイルへリンクする。

## 5. 実装のあとで突き合わせる

実装が終わったら（backend-impl・frontend-impl の最後）、次を1つずつ確かめる。食い違いがあれば、コードか詳細設計のどちらかを直す（設計書と食い違うなら、人に知らせる）。

- [ ] 機能全体 2章のクラス・ファイルが、すべてある。書いていないクラス・ファイルがない。
- [ ] API詳細 7章の SQL と、XML の SQL が同じ。
- [ ] API詳細 6・9章、画面詳細 4・9章の文と、コードの文が同じ。
- [ ] 版を上げ、変更履歴に書いた。

## 6. 設計書が直ったとき

設計書が直ったと人から聞いたら、直った章を「写したもと」に書いているファイルを Document の中で探し（例：`画面設計.md v1.1 の16章` で検索）、写した所と版を直す。中の作りまで変わるなら、人に知らせて、別の作業（backend-impl・frontend-impl）にする。

画面設計.md・データ設計.md などの設計書そのものは、自分で直さない（CLAUDE.md 2章）。

詳細設計は成果物の zip に入れる（deliver-zip の skill）。
