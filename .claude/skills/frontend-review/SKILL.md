# フロントエンドのレビュー（Client）

レビューする対象：$ARGUMENTS

あなたは、備品管理システムの画面のコードをレビューする。**ファイルを作る・直す・消すことはしない。** Git の作業も何もしない（状態を見るだけのコマンドも動かさない）。テストも動かさない（結果は、作業メモと、残っているテストの結果のファイルを読む）。結果は、最後に決まった形の文章で返す。

## 1. 何をレビューするかを決める

| 指定 | 変わったファイルの見つけ方 |
|---|---|
| タスク名か Jira の課題キー（例：種別管理、ZPOP-33） | Server か Client のいちばん上の、作業記録 `output/種別管理/`（課題キーが渡されたら、`output/` の中の各フォルダの作業メモ.md の頭の課題キーで探す）の `変更ファイル一覧.md` と `作業メモ.md` を読む（形は deliver-zip の skill の「作業記録の形」） |
| `output/` の中のフォルダ（作業記録、または zip の前のフォルダ） | そのフォルダの `変更ファイル一覧.md`（あれば `作業メモ.md` も）を読む |
| 相手から受け取った zip を広げたフォルダ | その中の `変更ファイル一覧.md` と `説明.md` を読み、`EquipmentManagementSystem_Client/` の中のファイルをレビューする |
| ファイル・フォルダのパス | そのファイル、またはそのフォルダの中の .ts・.tsx |
| 何もない | 人に対象を聞く（自分で決めつけない） |

変更ファイル一覧.md がなければ、そのことを結果に書き、指定されたパスだけをレビューする。Client のファイルが1つもなければ「Client の変更なし」と返して終わる。

Client のフォルダ（`EquipmentManagementSystem_Client`）と Document のフォルダが読めなければ、そのことを結果に書いて終わる（人が `/add-dir ../EquipmentManagementSystem_Client` で読めるようにしてから、もう一度呼ぶ）。

## 2. 照らし合わせるものを読む

同じフォルダに並んだ Document リポジトリ（`../EquipmentManagementSystem_Document`）の中を読む。

- [ ] `internaldesign/CLAUDE.md`（とくに 2章、3章、4.3、5章、6章、9章）
- [ ] その機能の詳細設計 `internaldesign/詳細設計/<機能名>/`（機能全体と、変わった画面の画面詳細）と、`common.md` 11章
- [ ] `externaldesign/画面設計.md` の1章と、その画面の章。`externaldesign/画面一覧.md`（スマートフォン優先かどうか）
- [ ] 画面が呼ぶ API の章（`internaldesign/API設計.md`）
- [ ] `internaldesign/テスト方針.md` 5章と、作業メモのテストの結果、Client の `playwright-report/`（あれば。zip の前のフォルダなら evidence のテスト結果.md）
- [ ] 心得：`.claude/skills/implementation-guidelines/SKILL.md`（6・8章）

## 3. 確かめること

1つずつ確かめ、合っていない所を指摘にする。推測で指摘しない。ファイル名と行番号、根拠（CLAUDE.md の章、設計書の章）を必ず示す。

**画面設計のとおりか**
- [ ] 項目・ボタン・画面の移り方が、画面設計と同じ。設計書にないボタンや動きを足していない。
- [ ] 画面設計に書いていない表示は、文のないもの（読み込み中の印、処理中に押せなくする、など）だけ。画面設計にない文（例：「データがありません」）を足していない（CLAUDE.md 5章）。
- [ ] メッセージ・ボタンの名前・見出しの文が、画面設計の文と一字も違わない（コードの文字と設計書の文字を並べて比べる）。
- [ ] 入力チェックの決まり（必須・文字数・形）が画面設計と同じで、誤りは入力欄のすぐ下に出る。
- [ ] 完了は緑の帯、操作できなかったことは赤の帯（`useMessage`）。API のエラー（400・403・404・409）ごとの出し方が画面設計のとおり。
- [ ] 詳細設計とコードが食い違っていない。

**フォルダと部品の使い方**（CLAUDE.md 4.3・5章）
- [ ] `src/features/<機能名>/` の中が pages・components・api.ts・types.ts に分かれている。ファイル名に画面ID がない。
- [ ] ほかの機能（`src/features/<ほかの機能>/`）のものを import していない。使うのは自分の機能と common だけ。
- [ ] API は common/api の `apiGet`・`apiPost`・`apiPut`・`apiDelete`・`useApi` で呼んでいる。`fetch` を直接呼んでいない。
- [ ] 入力欄は MUI と `useState`。使わないと決めたライブラリ（TanStack Query、React Hook Form）や、新しいライブラリを使っていない（package.json が変わっていたら指摘）。
- [ ] 押すと処理が動くボタンは `SubmitButton`（処理が終わるまで押せない）。確認がいる操作は `ConfirmDialog`。
- [ ] 日付・空の値は common/format で表示している。
- [ ] `routes.tsx` と共通ヘッダーのメニューは、1行足しただけ。common の部品を変えていたら、「2人で相談が必要な変更」として指摘する（CLAUDE.md 9章）。

**スマートフォン**（S-01〜S-06、S-19）
- [ ] スマートフォンの幅（600px より狭い）で、横にスクロールしない並べ方になっている。
- [ ] ボタンが指で押しやすい大きさ（テーマの 44px 以上）を保っている（テーマの値を上書きしていない）。

**安全**
- [ ] 権限によるボタンの出し分けは common/auth を使っている。画面で隠すだけで済ませず、サーバー側でも確かめる作りになっている（API に権限の確認があるか、詳細設計を見る）。
- [ ] `dangerouslySetInnerHTML` など、外から入った文字を HTML として出す書き方がない。
- [ ] パスワード・合言葉を、画面の表示・console・URL の後ろの値に出していない。

**テスト**（テスト方針 5章、CLAUDE.md 6章）
- [ ] テストは `tests/<機能名>/` にある。
- [ ] 画面設計のボタンの動き・入力の誤りのメッセージ・操作できなかったときの表示を確かめている。
- [ ] スマートフォン優先の画面は、スマートフォンと PC の両方で動かしている。
- [ ] メッセージを画面設計の文そのもので確かめている（一部だけの一致で済ませていない）。
- [ ] 待ち時間を固定の数字（`waitForTimeout`）に頼っていない。頼っているなら理由が書いてある。
- [ ] 最後に動かしたテストが全部成功している（作業メモ、結果のファイル）。

**心得（implementation-guidelines）**
- `any` や `as` で型の確かめを消している、同じ情報を2つの状態に持っている、`useEffect` の依存する値や片付けが足りない、API のエラーを握りつぶしている、など。根拠を「implementation-guidelines ○章」と書き、重さは「直したほうがよい」以下にする（決まりではないため）。

**そのほか**
- 決まりにも心得にもないが、不具合になりそうな所（画面を離れたあとに値を書き込む、など）。根拠を「一般的な不具合の恐れ」と書き、重さは「直したほうがよい」以下にする。

## 4. 返す形

次の形の Markdown で返す。

```
# フロントエンドのレビュー結果（<対象>）

## 結論
（「このまま取り込んでよい」か「直してから取り込む」。理由を1〜2文）

## 指摘
| No. | 重さ | 場所 | 内容 | 根拠 | 直し方の案 |
|---|---|---|---|---|---|
| 1 | 必ず直す | src/features/…/XxxPage.tsx:42 | … | 画面設計 16章「…」 | … |

重さ：
- 必ず直す：決まり・設計書に反する、不具合、安全の問題
- 直したほうがよい：読みにくい、テストが足りない、将来の不具合の恐れ
- 確認したい：設計書があいまいで、判断が要るもの

## 2人で相談が必要な変更
（common、routes.tsx の1行を超える変更、package.json などの変更。なければ「なし」）

## 確かめた観点
（3章の見出しごとに「問題なし」か「指摘 No.○」）

## 読んだもの
（レビューしたファイルの数と、読んだ設計書の章）
```

指摘がなければ、表に「なし」と書く。指摘を作るために、無理に探さない。
