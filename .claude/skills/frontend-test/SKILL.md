## 1. 何を確かめるかを、画面設計から決める

テストは**画面設計から**考える。コードを読んで「このとおり動くこと」を確かめるだけのテストにしない。

読むもの：その画面の画面設計（項目、入力チェック、メッセージ、ボタンの動き、操作できなかったときの表示）、画面一覧 7章（スマートフォン優先か）、詳細設計（画面詳細の4章の入力チェック、5章の操作、6章の状態、8章の移り方、9章のメッセージ）、テスト方針 5章。

| 観点 | 例 |
|---|---|
| 成功の流れ | 入力して押すと、画面設計の完了の文が緑の帯で出て、一覧などが変わる |
| 入力の誤り | 入力欄のすぐ下に、画面設計の文がそのまま出る。上限ちょうどは通り、1つ多いと出る |
| 操作できなかったとき | API が 400・403・409 などを返したとき、画面設計のとおりの表示（赤の帯など）になる |
| 二重押し | 押したボタンが、処理が終わるまで押せない |
| 確認ダイアログ | 「キャンセル」で何も起きない。実行すると1回だけ動く |
| 画面の移り方 | ボタン・リンクで、画面一覧のとおりの画面に移る |
| 権限 | 権限のない人には、画面設計のとおりボタンが出ない（ログインのタスクのあと） |
| スマートフォン | スマートフォン優先の画面は、スマートフォンの大きさで横にスクロールしない |

## 2. テストを書く

手本は `tests/common/`（category ができたら `tests/category/`）。

- [ ] `tests/<機能名>/` に置く。
- [ ] スマートフォン優先の画面（S-01〜S-06、S-19）は、スマートフォンと PC の両方で動かす。ほかの画面は PC だけでよい（common.md 11.7）。
- [ ] 画面の文は、画面設計の文そのもので確かめる（一部だけ一致、で済ませない）。
- [ ] 待つときは、表示を待つ書き方（`expect(...).toBeVisible()` など）にする。決まった時間だけ待つ書き方（`waitForTimeout`）に頼らない。
- [ ] テストの前に必要なデータは、テスト方針 5章（決まったデータを入れ直す）に合わせる。やり方がまだ決まっていなければ、作業メモの「確認してほしい点」に書いて人に確かめる。
- [ ] Slack には本物を送らない。
- [ ] テストの名前は、何を確かめるかを日本語で書く。証跡の一覧にそのまま出るため。

足した・変えたテストのファイルは、そのつど `output/<タスク名>/変更ファイル一覧.md` に書く。

## 3. テストを全部動かす

Server・Client のどちらを変えても、両方動かす（CLAUDE.md 6章）。

| どこで | コマンド |
|---|---|
| Server のフォルダ | `./gradlew test`（PowerShell なら `.\gradlew.bat test`） |
| Client のフォルダ | `npx playwright test` |

`npx playwright test` の前に、開発用の設定で起動したサーバー（8080番）を止めておく。Playwright は、すでに動いているサーバーをそのまま使うため、開発用のデータベース（equipment_dev）でテストが動いてしまう。

## 4. 失敗したとき

1. 失敗の文、`test-results/` の最後の画面とトレース（操作の記録）を見て、**画面設計と比べて**、テストとコードのどちらが違うかを決める。
2. コードが画面設計と違う → コードを直す（必要な所だけ）。直したファイルを変更ファイル一覧に、直した理由を作業メモに書く。詳細設計も直す。
3. テストが画面設計と違う（書き間違い） → テストを直す。作業メモに理由を書く。
4. たまにだけ失敗する → 待ち方を見直す（表示を待つ書き方にする）。待つ時間を延ばすだけで済ませない。
5. 画面設計があいまい・食い違う、または原因が分からない → 止めて人に知らせる。

**しないこと**：テストを消す、期待する結果を、今の動きに合わせて書き換える、確かめる中身を減らす（CLAUDE.md 6章）。
