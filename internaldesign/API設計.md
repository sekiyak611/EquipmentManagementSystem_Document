## 1. この資料について

API＝画面（React）とサーバー（Spring Boot）がデータをやり取りする窓口。画面は、ボタンが押されたときなどにAPIを呼び出し、サーバーはデータベースを読み書きして結果を返す。この資料では、APIの一覧と、それぞれで送る値・返す値・エラーを決める。

Claude Codeは、この資料をもとに、サーバー側のAPI（Spring Boot）と、画面側の呼び出し（React）と、APIのテスト（JUnit）を作る。

## 2. 共通の決まり

### 2.1 基本

| 項目 | 決まり | 説明 |
|---|---|---|
| 置き場所 | 画面とAPIを同じアドレスで出す。APIは /api/ で始まる | Spring Bootが、Reactで作った画面のファイルも一緒に配る形にする。画面とAPIのアドレスが違うと、ブラウザの安全のための制限（CORS）の設定が要り、ログインの扱いも難しくなるため |
| やり取りの形 | JSON（データを文字で表す決まった書き方）。文字コードはUTF-8 | ファイルのアップロード・ダウンロードだけは別の形（2.6） |
| 操作の種類 | GET＝読む、POST＝作る・実行する、PUT＝変える、DELETE＝消す | HTTPメソッドと呼ぶ |
| 日付 | "2026-11-02" の形 | 画面に出すときに 2026/11/02 の形に直す |
| 日時 | "2026-11-25T09:00:00+09:00" の形（日本時間） | |
| 列名 | 英語の小文字から始め、単語の区切りを大文字にする（例：managementNo） | Javaと画面のプログラムで一般的な書き方 |

### 2.2 ログインの仕組み

| 項目 | 決まり | 説明 |
|---|---|---|
| ログイン状態 | ログインに成功すると、サーバーがクッキー（ブラウザに保存される小さな情報）でログイン状態を渡す。以後のAPIでは、ブラウザがそのクッキーを自動で送る | セッションと呼ぶ。クッキーは、プログラムから読めない設定（HttpOnly）と、HTTPSのときだけ送る設定（Secure）にする |
| なりすまし対策 | 画面からのPOST・PUT・DELETEには、CSRFトークン（ほかのサイトから勝手に操作させる攻撃を防ぐ合言葉）を付ける | Spring Securityの仕組みを使う。サーバーが XSRF-TOKEN という名前のクッキーで合言葉を渡し、画面は X-XSRF-TOKEN という見出し（ヘッダー）に入れて送り返す |
| 権限の確認 | APIを呼ぶたびに、サーバーがログインしている人の権限項目を確かめる | 画面でボタンを隠すだけにしない（機能一覧4章の共通ルール）。権限の変更は次の操作から効く（機能一覧8章の7） |
| 強制ログアウト | APIを呼ぶたびに、ログインした日時が users.session_valid_after より前なら、ログアウトさせる | パスワードを変えたあと、ほかの端末を締め出すため（データ設計5.1） |

### 2.3 結果の伝え方（HTTPステータス）

HTTPステータス＝APIの結果を表す3桁の番号。

| 番号 | 意味 | 使う場面 |
|---|---|---|
| 200 | 成功（中身あり） | 読む、変えた結果を返す |
| 201 | 作った | 登録した |
| 202 | 受け付けた | パスワード設定用のリンクの依頼（A-04）。送れたかどうかは知らせない |
| 204 | 成功（中身なし） | 消した、パスワードを変えた |
| 400 | 入力の誤り | 必須が空、文字数オーバー、CSVの行のエラーなど |
| 401 | ログインしていない | ログインが切れた。画面はS-01に移る |
| 403 | 権限がない | 画面はS-19（権限がない）を出す |
| 404 | 見つからない | 削除された備品など。画面はS-19（見つからない）を出す |
| 409 | ぶつかった | ほかの人が先に保存していた（楽観ロック）、すでに貸し出されている、すでに返却されている |
| 500 | サーバーの不具合 | 画面はS-19（問題が発生しました）を出す。詳しい中身はログにだけ残す |

### 2.4 エラーのときに返す形

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容に誤りがあります",
  "fieldErrors": [
    { "field": "email", "message": "メールアドレスの形が正しくありません" }
  ]
}
```

| code | 意味 |
|---|---|
| VALIDATION_ERROR | 入力の誤り（400）。fieldErrors に、入力欄ごとのメッセージを入れる。メッセージは画面設計に書いたものと同じ文にする |
| UNAUTHORIZED | ログインしていない（401） |
| FORBIDDEN | 権限がない（403） |
| NOT_FOUND | 見つからない（404） |
| CONFLICT_VERSION | ほかの人が先に保存していた（409） |
| ALREADY_LENT | すでに貸し出されている（409） |
| ALREADY_RETURNED | すでに返却されている（409） |
| BUSINESS_RULE | 決まりに合わない操作（400）。例：貸出中の備品の削除、使われている種別の削除。message に画面設計のメッセージを入れる |
| CSV_ERROR | CSVの行にエラーがある（400）。rowErrors に、行番号・管理番号・理由を入れる |
| INTERNAL_ERROR | サーバーの不具合（500） |

### 2.5 一覧のページ分け

一覧を返すAPIは、page（何ページ目か。1から数える）を受け取り、次の形で返す。1ページの件数は画面設計の決まり（S-06は20件、ほかは50件）。

```json
{ "items": [ ... ], "page": 1, "size": 50, "totalCount": 128, "totalPages": 3 }
```

### 2.6 ファイルのやり取り

| 方向 | 形 |
|---|---|
| アップロード（S-11・S-18） | multipart/form-data（ファイルを送るための形）。項目名は file |
| ダウンロード（S-11のテンプレート） | text/csv。ファイル名は画面設計14章のとおり |

### 2.7 編集するAPIの決まり

備品・ユーザ・種別・権限・貸出履歴を変えるAPI（PUT）は、画面を開いたときに受け取った version を送る。サーバーの version と違えば、保存せずに 409（CONFLICT_VERSION）を返す（データ設計2章の楽観ロック）。

### 3.10 APIではない処理

| 処理 | 動き方 |
|---|---|
| Slack催促（機能一覧F-10） | サーバーの中で、決まった日時に自動で動く（Springの定期実行の仕組みを使う）。毎朝9:00に動き、今日が平日で、その月の催促日（25日。土日祝日なら前の平日）か、それより後で、その月にまだ送っていなければ送る。催促日にシステムが止まっていても、動き出したあとの平日に送るため。同じ月に2回送らないよう、reminder_runs の対象の月で確かめる（データ設計5.10、基本設計書7章） |
| 祝日の取り込み | 開発者が年1回、SQLで入れる（機能一覧7章の2） |
| 見張り役（基本設計書8章） | アプリとは別のプログラム（AWSのLambda、Java 21）。5分ごとに、CloudFrontのアドレスの A-08 を呼ぶ。10秒以内に 200 が返らなければ失敗とする。2回続けて失敗したら「止まっている」とし、開発者2人にDMを送る（画面設計9章の⑥）。その後、成功したら「戻った」とし、DMを送る（⑦）。今の状態（動いている／止まっている）と、続けて失敗した回数は、パラメータストア（6章）に保存する。状態が変わったときだけDMを送るので、止まっている間に同じ通知を繰り返さない |

## 4. 主なAPIの中身

すべてのAPIで、入力のチェックとメッセージは画面設計に書いたとおりにする。ここでは、とくに大事なAPIの送る値・返す値を例で示す。

### 4.1 A-01 ログイン

送る値

```json
{ "email": "yamada@example.com", "password": "（パスワード）", "rememberMe": true }
```

| 結果 | 返す値 |
|---|---|
| 成功 | 200。A-03と同じ形でログインした人の情報 |
| メールアドレスかパスワードが違う、削除されたユーザ、ロック中 | どれも 401。message は「メールアドレスまたはパスワードが違います」（画面設計2章） |

rememberMe が true なら、「ログインしたままにする」のクッキー（60日間）も渡す。

### 4.2 A-03 ログインしている人の情報

```json
{
  "id": 12,
  "name": "山田 太郎",
  "email": "yamada@example.com",
  "roleName": "一般社員",
  "permissions": ["LOAN_SELF", "CONFIRM_SELF"],
  "homePage": "MY_EQUIPMENT"
}
```

homePage は、ログインしたあと最初に出す画面。EQUIPMENT_VIEW を持っていれば EQUIPMENT_LIST（S-07）、持っていなければ MY_EQUIPMENT（S-05）。

### 4.3 A-04 パスワード設定用のリンクの依頼

送る値 `{ "email": "yamada@example.com" }`。登録の有無・5分以内の依頼・DMを送れたかにかかわらず、いつも 202（受け付けた）を返し、中身は返さない（画面設計5章）。

### 4.4 A-06 新しいパスワードを決める

```json
{ "token": "（リンクの合言葉）", "password": "（新しいパスワード）", "passwordConfirm": "（同じもの）" }
```

| 結果 | 返す値 |
|---|---|
| 成功 | 204。画面設計6章の1〜5をまとめて行う |
| 合言葉が使えない（期限切れ・使用済み・より新しいリンクがある） | 400、code は BUSINESS_RULE、message は「このリンクは使えません。有効期限が切れたか、すでに使われています。」 |
| パスワードの決まりに合わない | 400、VALIDATION_ERROR（画面設計8章のメッセージ） |

### 4.5 B-01 自分が借りている備品

```json
{
  "unconfirmedCount": 1,
  "reminderAt": "2026-11-25T09:00:00+09:00",
  "reminderPassed": false,
  "items": [
    {
      "loanId": 301,
      "equipmentId": 15,
      "managementNo": "A001",
      "categoryName": "PC",
      "maker": "Lenovo",
      "model": "ThinkPad X1",
      "lentOn": "2026-10-01",
      "dueOn": null,
      "overdue": false,
      "lastConfirmedOn": "2026-10-20",
      "confirmedThisMonth": false
    }
  ]
}
```

items は、未確認を上にし、その中は貸出日の古い順（画面設計3章）。reminderAt は今月の催促日時（25日。土日祝日なら前の平日）。

### 4.6 B-02 備品を借りる

送る値 `{ "equipmentId": 18, "dueOn": "2026-11-30" }`（dueOn はなくてもよい）

| 結果 | 返す値 |
|---|---|
| 成功 | 201。作った貸出履歴（B-01の items の1件と同じ形） |
| ほかの人が先に借りた | 409、code は ALREADY_LENT、message は「この備品はすでに貸し出されています」 |
| 管理中でない、削除された備品 | 400、BUSINESS_RULE |

貸出日はサーバーが今日の日付を入れる（送られても使わない）。あわせて、その備品の最終確認日を今日にする（機能一覧5章の6）。

### 4.7 B-04 確認した

送る値 `{ "equipmentIds": [15, 22] }`（1件のときも配列で送る）

自分が借りていない備品が1つでも含まれていたら、どれも更新せず 403 を返す。成功したら 200 で、B-01と同じ形の最新の一覧を返す（画面を更新しやすくするため）。

### 4.8 C-01 備品を探す

受け取る条件（アドレスの後ろに ? を付けて送る）

| 名前 | 内容 | 例 |
|---|---|---|
| keyword | 管理番号・メーカー・モデル・シリアルNo・借用者の氏名 | keyword=lenovo |
| categoryId | 種別のID | categoryId=1 |
| status | 管理状態。複数指定できる | status=MANAGED&status=MISSING |
| loanStatus | ALL／IN_STOCK（保管中）／LENT（貸出中） | loanStatus=IN_STOCK |
| confirm | ALL／CONFIRMED（今月確認済み）／UNCONFIRMED（未確認） | confirm=UNCONFIRMED |
| sort | managementNo／lastConfirmedOn。後ろに ,desc を付けると逆順 | sort=lastConfirmedOn,desc |
| page | ページ | page=2 |

items の1件には、画面設計10章の列と、色分けに使う confirmedThisMonth、id を入れる。

## 5. APIのテスト（JUnit）の方針

| 項目 | 方針 |
|---|---|
| テストする範囲 | すべてのAPIについて、成功、入力の誤り、権限がないとき（403）、ログインしていないとき（401）を確かめる |
| 権限 | 各APIで「必要な権限項目を持たない人」が呼んだら 403 になることを、必ず確かめる。画面でボタンを隠していても、APIを直接呼ばれる可能性があるため |
| データベース | 本物のMySQLを使ってテストする。自分のPCのMySQL（Docker で動かす。基本設計書 9章）に、テスト専用のデータベースを1つ作り、テストを始める前にFlywayでテーブルを作り直す。照合順序（データ設計2章）や生成列など、MySQL独自の動きも確かめるため。詳しくはテスト方針 |
| Slack | テストでは本物のSlackに送らず、送った内容を記録するだけの偽物に置き換える |
| 証跡 | テスト結果のレポートを、テスト方針（WBSの5.2）で決めた場所に保存する |

## 6. サーバーの設定値と秘密の値

プログラムを直さずに変えられるよう、次の値は設定として外に出す。秘密の値は、プログラムや、Gitで管理するファイルには書かない（CLAUDE.md 5章）。

| 設定 | 値 | 置き場所 |
|---|---|---|
| アプリのアドレス | DMに入れるリンクのもとになるアドレス。開発ではPCのアドレス、AWSではCloudFrontのアドレス（https://（英数字）.cloudfront.net） | 環境ごとの設定 |
| 時刻の基準 | 日本時間（Asia/Tokyo） | 設定ファイル |
| 催促の処理を動かす時刻 | 毎朝9:00。Springの書き方では "0 0 9 * * *"（秒・分・時・日・月・曜日の順）。テストでは変えられる | 設定ファイル |
| ログインしたままにする期間 | 60日 | 設定ファイル |
| パスワード設定用のリンクの有効期限 | 再設定・ロックは30分、ユーザ登録は3日 | 設定ファイル |
| 再設定の依頼の間隔 | 同じメールアドレスへは5分に1回まで | 設定ファイル |
| ロックまでの回数 | 5回 | 設定ファイル |
| CSVの大きさの上限 | 1MB | 設定ファイル |
| データベースの接続先・ユーザ名 | 開発は equipment_dev（自動テストは equipment_test）、AWSはRDS | 環境ごとの設定 |
| データベースのパスワード | 秘密 | 開発はGitで管理しない設定ファイル、AWSはパラメータストア |
| Slackのボットトークン | 秘密。Slackアプリの合言葉 | 同上 |
| 最初の総務の担当者のメールアドレス | 秘密（個人の情報のため） | 同上 |
| 見張り役の通知先 | 開発者2人のメールアドレス（Slackのユーザーを探すのに使う） | パラメータストア |
| 見張り役の状態 | 動いている／止まっている、続けて失敗した回数 | パラメータストア（見張り役が書き換える） |
| テスト用の切り替え | Slackを偽物にする、送った内容を読み出すAPIを動かす（テスト方針5章） | テストのときだけ有効になる設定。本番の設定では必ず無効 |

## 7. ログ（システムの記録）

| 項目 | 決まり |
|---|---|
| 残すこと | ログインの成功・失敗、ロック、パスワードの変更・再設定、権限の変更、データの登録・変更・削除（だれが・何を）、催促の結果、DMを送れなかったこと、エラーの詳しい内容 |
| 残さないこと | パスワード、パスワード設定用のリンクの合言葉、Slackのトークン、クッキーの中身 |
| 1件の形 | 1行に1件。日時・重要度（INFO／WARN／ERRORなど）・操作した人のユーザID・内容 |
| 置き場所 | 開発は各自のPCのファイル、AWSは CloudWatch Logs（AWSのログ保管サービス） |
| 保管期間 | AWSでは90日 |

## 8. 決めたこと

1. 画面とAPIを同じアドレスで出す（2.1）。
2. Slack催促の定期実行は毎朝9:00に動かし、その日が催促日かどうかをプログラムで判断する（3.10）。
3. APIのテストでは、自分のPCのMySQLに作ったテスト専用のデータベースを使う（5章）。
