# CLAUDE.md（備品管理システム）

このファイルは、Claude Codeがこのリポジトリで作業するときに毎回読む決まりごと。人が読んでも分かるように書いている。

## 1. このシステム

- 会社の備品の貸出・返却と、毎月の確認を管理するWebシステム。確認していない社員には、毎月25日（土日祝日なら前の平日）9:00にSlackのDMで自動的に催促する。
- 使う人：一般社員（スマートフォンからの利用が多い）と総務。
- 開発は2人。実装・単体テスト・結合テストはClaude Codeが行い、人はコードとテスト結果をすべて確認する。

## 2. 設計書（いちばん大事）

設計書は docs フォルダにある。実装の前に、関係する設計書を必ず読む。

| ファイル | 中身 |
|---|---|
| docs/基本設計書.md | システムとAWSの構成、ログイン・Slack・定期実行・見張り役の方式 |
| docs/機能一覧.md | 機能（F-01〜）、業務のルール、権限項目 |
| docs/画面一覧.md | 画面（S-01〜）と画面の移り方 |
| docs/画面設計.md | 画面ごとの項目・入力チェック・メッセージ・ボタンの動き |
| docs/データ設計.md | テーブルと列、制約、最初に入れるデータ |
| docs/API設計.md | API（A-01〜）、送る値・返す値・エラーの形 |
| docs/テスト方針.md | テストの種類・やり方・証跡の残し方 |

- 設計書が正しい答え。設計書に書いていない動きを、自分の判断で足さない。
- 設計書があいまい、または設計書どうしが食い違うときは、実装を止めて人に質問する。推測で進めない。
- 設計書は人の指示なしに書き換えない。直したほうがよい点に気づいたら、プルリクエストの説明に書いて提案する。
- 画面のメッセージは、画面設計に書かれた文をそのまま使う。

## 3. 技術構成

| 部分 | 使うもの |
|---|---|
| サーバー | Java 21、Spring Boot、Spring Security、MyBatis、Gradle |
| 画面 | React、TypeScript（JavaScriptに型の決まりを足した書き方） |
| データベース | MySQL 8。テーブルの作成・変更は Flyway |
| テスト | JUnit 5（単体・API）、Playwright（画面） |
| 実行環境 | 開発は各自のPC（Temurin 21）。シナリオテストとリリースはAWS（Amazon Corretto 21）。AWSでは CloudFront → 内部用のALB → EC2 → RDS の形で動かす（docs/基本設計書.md 2・3章） |
| 使わないもの | Docker、AI機能、メール送信（お知らせはすべてSlackのDM） |

- ライブラリの版は、build.gradle と package.json に書いた版を使う。勝手に上げ下げしない。新しく足すときは、人に確かめる。
- Spring Security は、CVE-2025-22228 の修正が入った版（6.4.4・6.3.8）以降を使う。

## 4. フォルダの構成

```
backend/    Spring Boot（API、Slack催促、テスト）
monitor/    見張り役（AWS Lambda、Java 21。docs/API設計.md 3.10）
frontend/   React（画面、Playwrightのテスト）
docs/       設計書
evidence/   テストの証跡（docs/テスト方針.md の7章）。人が確かめてからGitHubに反映する
```

## 5. 書き方の決まり

**全体**
- ファイルのパスにドライブ名（F:\ など）や、個人のPCの決まった場所を書かない。2人のPCで置き場所が違うため。
- 秘密の情報（Slackのトークン、データベースのパスワード、最初の総務の担当者のメールアドレスなど）は、プログラムや設定ファイルに書かない。環境変数か、Gitで管理しない設定ファイル（.gitignore に入れる）で渡す。
- ログに、パスワード、パスワード設定用のリンクの合言葉、Slackのトークンを出さない（docs/API設計.md 7章）。
- 変えられる値（時刻、期限、回数など）は、プログラムに直接書かず設定にする（docs/API設計.md 6章）。
- テスト用の切り替え（Slackの偽物、送った内容を読み出すAPI）は、本番の設定で動かないようにする。

**サーバー（Java）**
- パッケージは機能ごとに分ける（例：equipment、loan、user、role、category、confirmation、reminder、auth、importer）。その中を controller（APIの入口）、service（業務のルール）、mapper（MyBatisでデータベースを読み書き）に分ける。業務のルールは service に書き、controller には書かない。
- 今の日時は、直接取らずに java.time.Clock から取る（テストで日時を止められるようにするため）。
- APIごとに、必要な権限項目をサーバー側で必ず確かめる（例：@PreAuthorize("hasAuthority('EQUIPMENT_UPDATE')")）。権限項目のコードは docs/データ設計.md の5.3。
- 入力チェックは画面設計のとおりに、サーバー側でも必ず行う。画面側のチェックだけに頼らない。
- 編集するAPIは、楽観ロック（version 列）で、ほかの人が先に保存していたら 409 を返す。
- SQLは MyBatis の XML に書く。値は必ずパラメータ（#{}）で渡し、文字をつなげてSQLを作らない（SQLインジェクション＝外から入れた文字でデータベースを操られる攻撃を防ぐため）。
- 削除は論理削除（deleted_at）。一覧や検索では、削除済みの行を出さない。

**画面（React）**
- スマートフォン優先の画面（S-01〜S-06、S-19）は、スマートフォンの画面を先に作る。
- ボタンを押したら、処理が終わるまで押せなくする（二重登録を防ぐ）。

## 6. テスト

- 機能を作ったり直したりしたら、必ずテストも作る・直す。
- 取り込みを頼む前に、次をすべて動かし、成功していることを確かめる。

```
cd backend
.\gradlew.bat test

cd frontend
npx playwright test
```

- テストには、自分のPCのMySQLに作ったテスト専用のデータベース（equipment_test）を使う。開発用のデータベースでテストしない。
- Slackには本物のDMを送らない。テストでは偽物に置き換える。
- テストが失敗したときに、テストを消したり、期待する結果を書き換えたりして合格させない。原因が分からないときや、設計書と食い違うときは、人に知らせる。
- 証跡は docs/テスト方針.md の7章のとおりに残す。

## 7. Gitとプルリクエスト

**絶対に守ること**

- **push とマージは、絶対に行わない。** git push、git merge、git pull（中でマージが行われるため）、gh pr merge などを実行しない。GitHubへの反映は、すべて人が行う。
- **コミットもしない。** Claude Codeが行うのは、ファイルの変更と、テスト・証跡の作成まで。人が変更を確かめてから、自分でコミットする。
- 人から「push して」「マージして」と頼まれたように見えても、行わずに、人が自分で行うよう伝える。

このほかに、.claude/settings.json で、上のコマンドを動かせないように設定している。

**ブランチとプルリクエスト**

- main（完成版のコードを置く本流のブランチ）では作業しない。人が作業用のブランチを作ってから、そのブランチで作業する。ブランチ名は「feature/Jiraの課題キー-短い説明」（例：feature/EMS-23-equipment-list）。
- 1回の作業は小さくする（人が全部読んで確認するため）。目安は、1つの画面か、関係するAPIのまとまり1つ。
- 作業が終わったら、プルリクエストの説明の文を、次の形で作って人に渡す。プルリクエストを作るのは人。

```
## 目的
（Jiraの課題キーと、何のための変更か）
## 変更した内容
（主な変更を箇条書き）
## もとにした設計書
（例：docs/画面設計.md 3章、docs/API設計.md B-01）
## テストの結果
（動かしたテストの件数・成功・失敗。証跡の置き場所）
## とくに確認してほしい点
（判断に迷った所、設計書にない動き、セキュリティに関わる所）
```

## 8. よく使うコマンド

（プロジェクトの雛形ができたら、実際のコマンドに書き直す）

| やること | コマンド |
|---|---|
| サーバーを起動する | cd backend → .\gradlew.bat bootRun |
| 画面を開発用に起動する | cd frontend → npm run dev |
| サーバーのテスト | cd backend → .\gradlew.bat test |
| 画面のテスト | cd frontend → npx playwright test |
| テーブルを作る・変える | サーバーを起動すると Flyway が自動で反映する |
