## 1. この資料について

どんなテストを、だれが、どこで、どこまで行い、証跡（テストした証拠）をどう残すかを決める。Claude Codeは、この資料に沿ってテストを作り、動かし、証跡を残す。

## 2. テストの種類

| 種類 | 何を確かめるか | だれが作る・動かすか | 道具 | 動かす場所 |
|---|---|---|---|---|
| 単体テスト | 1つの部品（クラス）が正しく動くか。例：催促日の計算、パスワードの決まりのチェック | Claude Code | JUnit（Javaのテストの道具） | 自分のPC |
| 結合テスト（API） | APIを呼んで、データベースまで正しく読み書きできるか。権限のチェックも含む | Claude Code | JUnit＋Spring Bootのテストの仕組み | 自分のPC（テスト専用のデータベース） |
| 結合テスト（画面） | 画面を操作して、サーバー・データベースまで通しで動くか | Claude Code | Playwright（ブラウザを自動で操作する道具） | 自分のPC |
| シナリオテスト | 実際の業務の流れに沿って、システム全体を使って問題がないか | 人（2人） | 手で操作し、スクリーンショットを撮る | AWS |

人は、Claude Codeが作ったテストのプログラムと結果を、すべて確認する（プルリクエストで確認する。7章）。

## 3. 単体テスト

| 項目 | 方針 |
|---|---|
| 対象 | 計算や判断をする部品は必ず。とくに、催促日の計算（25日・土日祝日・前の平日）と、送るかどうかの判断（催促日に止まっていたときは、動き出したあとの平日に送る。月が替わったら送らない）、見張り役の判断（2回続けて失敗で「止まっている」、状態が変わったときだけ通知）、今月確認済みの判定、貸出の期間の重なりのチェック、パスワードの決まり、CSVの行のチェック、昇降・ピボットの読み取り（○・〇・◯・×） |
| 日付 | プログラムは「今の日時」を直接取らず、時計の部品（java.time.Clock）から取る。テストでは時計を好きな日時に止めて、「11月25日が水曜」「25日が日曜で23日が祝日」などを確かめる |
| 境界値 | 文字数の上限ちょうど（例：50文字）と1文字多い（51文字）、日付の前日・当日・翌日など、境目の両側を確かめる |

## 4. 結合テスト（API）

| 項目 | 方針 |
|---|---|
| 対象 | API設計の全API（48本） |
| 確かめること | APIごとに、①成功、②入力の誤り（400）、③ログインしていない（401）、④必要な権限項目がない（403）、⑤決まりに合わない操作・ぶつかったとき（400・409）。④は必ず確かめる |
| データベース | 自分のPCのMySQL（Docker で動かす。基本設計書 9章）に、テスト専用のデータベース（名前は equipment_test）を作る。データベースは、MySQL のコンテナを最初に作ったときに自動でできる（Server の docker/mysql/init）。テストを始める前に、Flywayでテーブルを作り直す。テストどうしが影響しないよう、1つのテストが終わるたびにデータを元に戻す |
| Slack | 本物には送らない。送った内容を記録するだけの偽物に置き換え、「だれに、どんな文を送ったか」を確かめる |
| 動かし方 | テストは1つずつ順番に動かす（同じデータベースを使うため） |

## 5. 結合テスト（画面）

| 項目 | 方針 |
|---|---|
| 対象 | 全19画面。画面設計に書いた、ボタンの動き・入力の誤りのメッセージ・操作できなかったときの表示 |
| 画面の大きさ | スマートフォン優先の画面（S-01〜S-06、S-19）は、スマートフォンとPCの両方の大きさで確かめる。ほかの画面はPCの大きさで確かめる（画面一覧7章） |
| 動かし方 | 自分のPCで、テスト用の設定にしたサーバーを起動し、Playwrightで画面を操作する。データベースは結合テスト（API）と同じ equipment_test を使い、テストの前に決まったデータを入れ直す |
| Slack | 結合テスト（API）と同じく偽物に置き換える。パスワード設定用のリンクのように、DMの中身を使うテストでは、テスト用の設定のときだけ動く「送った内容を読み出すAPI」を使う。この読み出し用のAPIは、本番では動かないようにし、そのことをテストでも確かめる |
| スクリーンショット | 各テストの最後の画面を残す。失敗したテストは、失敗した時点の画面と、操作の記録（Playwrightのトレース）を残す |

## 6. シナリオテスト

| 項目 | 方針 |
|---|---|
| 場所 | AWSの環境 |
| だれが | 人（2人）。担当するシナリオを分けて実施し、相手の結果を相互レビューする（お互いの結果を確認し合う） |
| シナリオ | 業務の流れごとに作る。例：①総務が備品を登録する → 社員が借りる → 確認する → 返す。②社員が月の途中まで確認しない → 25日に催促のDMが届く → DMのリンクから確認する → 催促履歴に残る。③パスワードを5回間違える → ロックされる → DMのリンクから再設定する。④総務が今のExcelのデータを一括登録する |
| 催促のテスト | 25日を待たずに試せるよう、送る日時を設定で変えて行う（機能一覧7章の9） |
| AWSならではのテスト | CloudFrontを通しても、ログイン・「ログインしたままにする」・CSRFトークン・CSVのアップロードとダウンロードが正しく動くこと。CloudFrontを通さずにALBやアプリへ直接つなごうとしても、つながらないこと |
| 見張り役のテスト | AWSでアプリを止め、開発者2人に「止まっています」のDMが届くこと。アプリを戻し、「戻りました」のDMが届くこと |
| Slack | 社内のSlackに入れたアプリで、開発者2人にだけ送るテストデータを使う |
| 合格の基準 | すべてのシナリオで、期待した結果になること。見つかった不具合は、すべて直して再テストするか、年明け以降に回すことを2人で合意していること |

## 7. 証跡（テストした証拠）

| テスト | 残すもの | 置き場所 |
|---|---|---|
| 単体・結合（API） | Gradleが作るテスト結果のレポート（HTML）。どのテストが成功・失敗したかの一覧 | 各自のPCのリポジトリの evidence フォルダ |
| 結合（画面） | Playwrightが作るレポート（HTML）と、スクリーンショット | 各自のPCのリポジトリの evidence フォルダ |
| シナリオテスト | シナリオテスト仕様書に、手順ごとの結果（OK／NG）、実施日、実施者、相互レビューをした人を書く。手順ごとのスクリーンショット | 各自のPCのリポジトリの evidence フォルダ |

**置き方とGitHubへの反映**（Q1の回答）

1. Claude Codeは、テストを動かしたら、証跡を自分のPCのリポジトリの evidence フォルダに保存する。
2. 人が証跡の中身を確かめてから、自分の手でGitHubのリポジトリに反映（コミット・push・マージ）する。
3. Claude Codeは、push とマージを絶対に行わない（CLAUDE.md の7章）。

**プルリクエストのたびに**：Claude Codeは、プルリクエスト（変更を本流に取り込む前の確認依頼）に書く説明の文を作り、テストを動かした結果（件数・成功・失敗）も入れる。プルリクエストを作るのと、取り込むのは人が行う。失敗しているテストがあるまま、取り込みを頼まない。

**ファイル名の付け方**：「日付_テストの種類_内容」の形にする（例：20261210_結合API_備品、20261222_シナリオ_催促）。

## 8. 不具合の扱い

| 項目 | 方針 |
|---|---|
| 記録 | 見つけた不具合は、Jiraに登録する。再現する手順、期待した結果、実際の結果、スクリーンショットを書く |
| 直し方 | Claude Codeに直させ、直したことを確かめるテストを足す（同じ不具合が二度と起きないように） |
| テストの扱い | テストが失敗したときに、テストのほうを消したり、期待する結果を書き換えたりして合格させない。設計書と食い違う場合は、人が判断する |
