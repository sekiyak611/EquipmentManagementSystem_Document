# 決まり：開発の流れ（工程・ゲート・Jira）

2026-11-22 に決めた。それまでは、AI が詳細設計から単体テストまでを1つの会話・1つのプルリクエストで通して行っていた。
CLAUDE.md 11章の本体。**工程を始める前に必ず読む。** 手順は skill の `phase-gate`（ゲート・Jira・次の提案）と、各工程の skill に書いた。

## 1. 3つの工程と、MR

MR は、GitHub のプルリクエストのこと。1つの MR は、Jira の1つのサブタスクに当たる。1つのストーリーを、3回の「作る → マージ → 確かめる」で進める。

| 工程 | Jira のサブタスク | 使う skill | 作るもの | MR を出す所 |
|---|---|---|---|---|
| ① 詳細設計 | `[詳細設計]` | spec-check → detailed-design → design-review | 詳細設計（Document） | Document |
| ② 実装 | `[実装]` | backend-impl・frontend-impl → backend-review・frontend-review | コード | Server か Client |
| ③ 単体テスト | `[単体テスト]` | backend-test・frontend-test → deliver（ut） | テストのコード、エビデンス（API は JUnit、画面は Playwright） | Server か Client と、Document（エビデンス）の2つ。同じ課題キー・同じブランチ名 |

## 2. 1つの工程の流れ（3つの工程で共通）

1. **始める**：Jira のサブタスクを「進行中」にする。役割（`DEV_ROLE`。9章）を確かめる。ゲート（3章）を確かめる。
2. **AI が作る**：skill の手順で。外から見える判断は、実装の前に、まとめて人に質問する（CLAUDE.md 2章）。
3. **独立した AI レビュー**：作った会話とは別のエージェントが、成果物を確認する（design-review・backend-review・frontend-review）。AI は、指摘を直す。
4. **人がチェック**：直しは、AI に頼むか、人が手で直す。**人が手で直したら、AI は `git diff` でその内容を読み**、詳細設計とコードの食い違いがないか確かめてから進む。
5. **MR を作る**：Jira のサブタスクを「確認中」にする。
   - `DEV_ROLE=junior`：MR を **Draft（下書き）** で作り、経験者かリーダーが MR の上でレビューする。承認されたら Ready にする。
   - `DEV_ROLE=senior`・`leader`：レビューは要らない。Ready で作る。
6. **リーダーがマージする**（AI はマージしない。CLAUDE.md 7章）。
7. **人が「マージした」と伝える** → AI が、ゲートの判定で確かめる → 合っていれば、Jira を「完了」にして、次にすることを提案する（7章）。

## 3. ゲート：前の工程がマージされているかを確かめる

AI は、**マージされたか**を、人の言葉だけで判断せず、`tools/check-merged.sh` で確かめる。

```
bash ../EquipmentManagementSystem_Document/tools/check-merged.sh <リポジトリのフォルダ> <サブタスクの課題キー>
```

1行目が `MERGED`／`NOT_MERGED`／`NOT_FOUND`／`ERROR`。`git fetch` でリモートの情報を更新するだけで、ほかは何も変えない（テストは `tools/test-check-merged.sh`）。判定のしかたは、スクリプトの先頭に書いた。

| ゲート | いつ | 調べるもの | `MERGED` | `NOT_MERGED`・`NOT_FOUND`・`ERROR` |
|---|---|---|---|---|
| A | 実装を始める前 | Document の `[詳細設計]` サブタスク | 実装へ進む | **警告して、別の機能の詳細設計を提案する。** 人が「それでも進める」と答えたときだけ、`NOT_MERGED` に限って進める（下の「設計が未マージのまま進むとき」）。`NOT_FOUND`・`ERROR` では進まない |
| B | 単体テストを始める前 | Server か Client の `[実装]` サブタスク | UT へ進む | **警告して、絶対に進まない。** 人が頼んでも進まない。別の機能の詳細設計を提案する |
| C | 単体テストの MR のあと | `[単体テスト]` サブタスク（テストのリポジトリと Document の両方） | 完了。次の機能の詳細設計を提案する | 未マージを知らせ、待つ（別の機能の詳細設計を提案する） |

**警告の文**（人に見せる）：「`[詳細設計]` の MR（`<キー>`）が、まだ release/main にマージされていません。…」のように、何が未マージで、どの工程に進めないかを書く。`NOT_MERGED` なら、未マージのブランチの名前も書く。

**設計が未マージのまま進むとき（ゲート A）**
- 設計は、Document の未マージのブランチから、`git show origin/<ブランチ>:<パス>` で読む（Document のフォルダのブランチは切り替えない）。
- 実装の MR は、**Draft のまま**にして、設計がマージされるまで Ready にしない。説明に「先に Document の #番号 を取り込む」と書く。
- 設計が、レビューで変わったら、実装も直す。直すのは、設計がマージされたあと、最新の設計と突き合わせてから。

**新しい作業を始めるとき**：`git checkout release/main` → `git pull --ff-only origin release/main`（早送りだけ。許可している）→ そこから作業用のブランチを切る。

## 4. ブランチ・MR・commit の名前

サブタスクの課題キーを使う（工程と MR を、キーで結び付けるため。`check-merged.sh` が探す）。

| もの | 決まり | 例 |
|---|---|---|
| ブランチ | `feature/<サブタスクの課題キー>-<英語の機能名>-<design・impl・ut>`。同じ工程では、リポジトリが違っても同じ名前 | `feature/ZPOP-169-b03-return-design` |
| 修正のブランチ | 同じキーのまま、末尾に `-fix`（6章） | `feature/ZPOP-169-b03-return-design-fix` |
| MR の名前 | `<サブタスクの課題キー> [工程] <タスク名>：…` | `ZPOP-169 [詳細設計] B-03 借りている備品を返す：…` |
| commit の1行目 | `<サブタスクの課題キー> <タスク名>：何をしたか` | `ZPOP-170 B-03：返却の API を作った` |

## 5. Jira の自動更新（2026-11-22 に、人が「自動で更新してよい」と決めた）

状態は「未着手 → 進行中 → 確認中 → 完了」。どの状態にも直接移せる。**変えるのは状態だけ**（コメントや内容は書かない）。更新に失敗したら、人に知らせて、作業は止めない。サイトの ID は、`getAccessibleAtlassianResources` で調べる（この文書には書かない）。

| 出来事 | サブタスク | ストーリー |
|---|---|---|
| 工程を始める | 進行中 | 未着手なら、進行中 |
| MR を作る（Draft を含む） | 確認中 | ― |
| ゲートで、マージを確かめた | 完了 | `[単体テスト]` が完了したら、完了 |
| 修正の MR を出す（6章） | 進行中（完了だったものを戻す） | 完了だったら、進行中に戻す |

サブタスクは、`parent = <ストーリーの課題キー>` で探し、名前の頭（`[詳細設計]`・`[実装]`・`[単体テスト]`）で見分ける。

## 6. 設計との食い違い・不具合が見つかったとき

実装や単体テストの途中で見つけたら、**止めて人に知らせ**、次のとおり、修正の MR を先に出す。

- **設計が違う（設計書や詳細設計の誤り・不足）**：Document に、設計の修正の MR（`…-design-fix`）。マージされるまで、実装・UT には進まない。
- **実装の不具合（UT で見つかった）**：実装の修正の MR（`…-impl-fix`）。マージされてから、UT に戻る。テストを、実装に合わせて書き換えない（CLAUDE.md 6章）。

## 7. 次の機能の提案

マージを待つあいだ、または、ゲートで止まったとき、AI は次の機能の詳細設計を提案する。

1. Document の `実装タスク一覧.md` の「先にやるタスク」を読み、**先にやるタスクの `[詳細設計]` が完了**（Jira）している機能だけを候補にする。
2. Jira で、`[詳細設計]` が「未着手」の機能を、タスクの順に並べる。
3. 候補が、**いま MR 待ちの設計と同じファイル**（common.md、テーブル.md など）を触りそうなら、マージのときにぶつかるので、そのことを添える。
4. 1〜3件を、理由とあわせて提案する。人が選んだら、その機能の詳細設計の工程を始める。

## 8. 積み重ねブランチ

前の MR がまだマージされていないときに、**同じリポジトリの中で**、その続きを書くことを、積み重ねという。前の MR のブランチから新しいブランチを切り、MR の「もと」も前のブランチにする（説明に「先に #番号 を取り込む」と書く）。

- 例：Document で、B-03 の設計の MR が未マージのまま、B-04 の設計を書く。B-04 の設計が、B-03 の設計が書いた common.md を使うとき。
- 設計（Document）と実装（Server）は、別のリポジトリなので、積み重ねにならない。ゲート A で進むときは、3章のとおり、設計のブランチを読むだけ。

## 9. 役割（`DEV_ROLE`）

人の役割を、環境変数 `DEV_ROLE` で AI に伝える。各自のPCの、Server・Client の `.claude/settings.local.json`（Git で管理しない）に書く。例のファイルは `internaldesign/settings-local/`（`settings.local.junior.json`・`.senior.json`・`.leader.json`）。

| `DEV_ROLE` | 意味 | 人のレビュー |
|---|---|---|
| `junior` | 経験が浅いメンバー | **要る**（MR を Draft で作り、経験者かリーダーがレビュー） |
| `senior` | 経験者のメンバー | 要らない |
| `leader` | リーダー（MR のマージも行う） | 要らない |

設定されていなければ、AI は、人にどれかを尋ね、ファイルの作り方を案内する（勝手に決めない）。AI は、`echo "${DEV_ROLE:-}"` で確かめる。

## 10. settings で許可していること

Server・Client の `.claude/settings.json`（Document の `internaldesign/settings.json` が見本）。

- 許可：`git fetch`、`git pull --ff-only origin release/main`、`tools/check-merged.sh`。
- 禁止（これまでどおり）：マージ・release/main への push・強制 push・rebase・それ以外の `git pull`（許可していないので、確認が出る）。
- `git pull` は、release/main の上でだけ行う（作業用のブランチの上では行わない）。
