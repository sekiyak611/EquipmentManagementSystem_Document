| 項目 | 内容 |
|---|---|
| 版 | v2.0 2026-11-08 |

## 1. この資料について

このフォルダ（Document リポジトリの internaldesign/詳細設計/）には、詳細設計を置く。

API設計・画面設計・データ設計は「何を作るか（外から見た動き）」を決める資料。それに対して詳細設計は、「どう作るか（中の作り）」を書く。どのクラスがあり、どの順番で何をし、どんな SQL を出すかを書く。あわせて、設計書に書いてある「何を作るか」も写し、1つのファイルを読めば実装できるようにする。

目的は2つ。

1. 人が、コードを読む前に作りの全体をつかめるようにする（コードとテストの確認がしやすくなる）。
2. 2人の Claude が、同じ考え方で作れるようにする（相手が作った機能の作りを、コードを読まずに知れる）。

## 2. ファイルの分け方

1つの機能（CLAUDE.md 4.1 のパッケージ）に1つのフォルダを作り、その中を「機能全体」「API ごと」「画面ごと」のファイルに分ける。

```
internaldesign/詳細設計/
├─ README.md                    この資料
├─ テンプレート/
│  ├─ 機能.md                    機能全体のテンプレート
│  ├─ API.md                     API詳細のテンプレート
│  └─ 画面.md                    画面詳細のテンプレート
├─ common.md                    共通部品（common）と基盤。この資料の形ではなく、部品のまとまりごとに章を立てる
├─ health/                      例（お手本）
│  ├─ health.md                  機能全体
│  └─ A-08_動いているかを答える.md  API詳細
└─ category/                    例
   ├─ category.md                機能全体
   ├─ K-01_….md 〜 K-04_….md     API詳細（API ごとに1つ）
   └─ S-13_種別管理.md            画面詳細（画面ごとに1つ）
```

| ファイル | 名前 | テンプレート | 中身 |
|---|---|---|---|
| 機能全体 | `<機能名>.md` | テンプレート/機能.md | 概要（API・画面・業務のルールの一覧）、クラス・ファイル構成、ほかの機能への影響、機能全体の設計書にない判断 |
| API詳細 | `<APIのID>_<短い名前>.md` | テンプレート/API.md | API基本情報、リクエスト定義、レスポンス定義、処理フロー、条件分岐・業務ルール、バリデーション仕様、DB操作仕様、トランザクション・排他制御、エラー処理仕様、認証・認可仕様、外部API連携仕様、設計書にない判断 |
| 画面詳細 | `<画面のID>_<短い名前>.md` | テンプレート/画面.md | 画面基本情報、画面レイアウト、画面項目定義、入力チェック仕様、イベント・操作仕様、画面状態・表示条件、API連携仕様、画面遷移仕様、メッセージ・エラー表示仕様、設計書にない判断 |

- 機能名・ID・短い名前は、API設計・画面一覧のものを使う。
- 詳細設計のファイル名には API・画面の ID を入れる（Client のソースのファイル名には画面IDを入れない決まり（CLAUDE.md 4.3）とは別）。
- 共通部品（common）は common.md に、部品のまとまり（common.config・common.security など）ごとの章を立てて書く。
- テストの一覧は詳細設計に書かない。テストの観点は設計書とテスト方針から決め（backend-test・frontend-test の skill）、書いたテストの一覧は証跡のテスト結果.md に残す。

## 3. 設計書の中身を写すときの決まり

詳細設計には、設計書（機能一覧・画面一覧・画面設計・API設計・データ設計）に書いてあることも写す。

1. **写した所には、写したもとを書く。** 「写したもと：画面設計.md v1.1 の16章」のように、ファイル名・版・章を書く。
2. **写すときは変えない。** 画面の文・メッセージ・表示名は一字も変えない。表は、列を足すのはよいが、設計書の行や値を変えない。
3. **食い違ったら設計書が正しい**（CLAUDE.md 2章）。写し間違いに気づいたら、詳細設計を直す。
4. **設計書が直ったら、写した詳細設計も直す。** 直した設計書の章を「写したもと」に書いているファイルを探し（例：`画面設計.md v1.1 の16章` で検索する）、写した所と版を直す。
5. 設計書に書いていないことを決めたら、写した所に混ぜずに「設計書にない判断」の章に書く。

## 4. いつ書くか

1. **実装の前に書く。** Jira のタスクを始めたら、まず関係する設計書を読み、テンプレートの形で書く（すでにファイルがあれば書き足す）。
2. **「設計書にない判断」で外から見えるもの**（返す値の項目、エラー、画面の文、移り方）は、実装の前に人に確かめる。
3. **詳細設計のとおりに実装する。** 実装の途中で作りを変えたら、詳細設計も同じように直す。最後に、詳細設計とコードが食い違っていないかを確かめる。
4. **成果物の zip に入れる**（CLAUDE.md 7章。zip の中の EquipmentManagementSystem_Document/internaldesign/詳細設計/<機能名>/）。

詳細設計は、設計書（API設計など）の決まりを変えるものではない。設計書と食い違う作りが必要になったら、詳細設計に書いて済ませず、実装を止めて人に質問する（CLAUDE.md 2章）。

書く手順は detailed-design の skill、コードから書き起こす手順は reverse-engineer の skill。

## 5. 書き方

- 当てはまらない章は、章ごと消さずに「なし」と書く（書き忘れと区別するため）。
- テンプレートの `<!-- … -->` の説明は、書き終えたら消す。
- 専門用語は、初めて出てくる所で短く説明する。
- クラス名・メソッド名・テーブル名・列名は、コードと同じ文字で書く。名前の付け方は CLAUDE.md 5章の命名規則。
- パッケージの頭の `jp.co.highjunk.equipment` は省いてよい。
- ほかのファイルを指すときは、相対のリンクにする（例：`[K-01_種別一覧.md](K-01_種別一覧.md)`）。

## 6. どの機能でも同じこと（詳細設計には書かない）

次のことは、機能ごとの詳細設計には書かず、下の場所を見る。詳細設計に書くのは、その機能で違う所だけ。

| こと | 書いてある場所 |
|---|---|
| フォルダ・パッケージの構成 | CLAUDE.md 4章（4.1 サーバー、4.3 画面） |
| 部品の役目の分け方（controller・service（interface と Impl）・validator・mapper など） | CLAUDE.md 4.1・5章、基本設計書 2・4章 |
| 書き方の決まり（JOIN を使わない、Clock から時刻を取る など） | CLAUDE.md 5章 |
| 名前の付け方 | CLAUDE.md 5章の命名規則 |
| 書き方の心得（読みやすさ、例外、型 など） | Document の .claude/skills/implementation-guidelines/SKILL.md |
| 共通の部品（返す値の形、例外、CSRF、時計、画面の共通部品） | common.md |
| エラーの返し方・ログの方針 | API設計 2.4・7章、common.md |
| テストのやり方 | テスト方針、CLAUDE.md 6章 |
