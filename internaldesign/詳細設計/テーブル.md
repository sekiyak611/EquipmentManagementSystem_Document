## 1. 概要

データ設計のテーブル13個と、最初に入れるデータを、Flyway（テーブルの変更を SQL のファイルで管理し、番号の順に自動で当てる道具）のファイルで作る。サーバーを起動したとき（テストのときは TestFlywayConfig が消してから）に、まだ当てていないファイルが自動で当たる（common.md 4章）。

この資料は、機能ではなく基盤なので、機能のテンプレートの形ではなく、次の章立てで書く。各テーブルの列（名前・型・必須・説明）はデータ設計 5章が正本で、ここには写さない（SQL のファイルが、そのまま列の一覧になっているため。7章の No.1）。ここには「データ設計をどう SQL にしたか」を書く。

| secret.example.yml | `app.initial-admin-email` の説明を直した |

| src/test/java/jp/co/highjunk/equipment/common/config/InitialAdminEmailCallbackTest.java | メールアドレスの確かめのテスト |

- ファイル名の `V1__`・`V2__` は Flyway の版の番号。一度当てたファイルは中身を変えない（変えると Flyway が「当てたあとに変わった」と止まる）。テーブルを足す・変えるときは、新しい番号のファイルを足す（CLAUDE.md 9章：先に相手に伝える）。
- テーブルを作るのと、データを入れるのを、ファイルで分けた。V2 はデータを入れるだけなので、途中で失敗しても、書き込みは全部元に戻る（MySQL は、テーブルを作る命令は元に戻せないため）。ただし Flyway の記録（flyway_schema_history）には「失敗した」が残り、人がその記録を消すまで起動できなくなる。そのため、失敗しそうな原因（メールアドレスの設定がない）は、当て始める前に確かめる（5章）。

## 3. SQL にするときの決まり（全テーブル共通）

写したもと：データ設計.md v1.0 の2章

| データ設計の決まり | SQL |
|---|---|
| 文字コード utf8mb4、照合順序 utf8mb4_ja_0900_as_cs_ks | どのテーブルにも `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_ja_0900_as_cs_ks` を付ける（データベースの初めの設定に頼らない） |
| id（自動で1ずつ増える） | `id BIGINT NOT NULL AUTO_INCREMENT` と、表の最後の `PRIMARY KEY (id)`。permissions・holidays・role_permissions・reminder_log_items・persistent_logins は持たない（データ設計 5章のとおり） |
| 論理削除 | `deleted_at DATETIME NULL` |
| version（楽観ロック） | `version INT NOT NULL DEFAULT 0`（7章の No.2） |
| 記録用の列 | `created_at DATETIME NOT NULL`、`created_by BIGINT NULL`、`updated_at DATETIME NOT NULL`、`updated_by BIGINT NULL`。持つのは、データ設計 5章で「記録用の列」と書いた users・roles・categories・equipment・loans だけ |
| 日時は日本時間（DATETIME） | 日時の列は `DATETIME`（秒まで）。値はプログラムが Clock から作って入れるので、データベースの初めの値（DEFAULT CURRENT_TIMESTAMP）は付けない |
| 削除済みを重複に数えない | 生成列（ほかの列から自動で計算される列）を `GENERATED ALWAYS AS (CASE WHEN deleted_at IS NULL THEN 列 END) STORED` で作り、`UNIQUE` を付ける。削除済みの行は空（NULL）になり、UNIQUE は空どうしの重複を許すのでぶつからない |
| 必須（○） | `NOT NULL`。○がない列は `NULL` |
| BOOLEAN | `BOOLEAN`（MySQL の中では TINYINT(1)。true が 1、false が 0） |

**名前の付け方**（SQL の中の制約と索引）

| もの | 名前 | 例 |
|---|---|---|
| UNIQUE | `uk_<テーブル>_<列>` | uk_categories_name_active |
| 外部キー | `fk_<テーブル>_<列>` | fk_users_role_id |
| CHECK | `ck_<テーブル>_<列>` | ck_equipment_status |
| 索引 | `idx_<テーブル>_<列>` | idx_equipment_category_id |

名前を付けておくと、エラーの文に名前が出るので、どの決まりに引っかかったかが分かる。

## 4. テーブルごとの作り

写したもと：データ設計.md v1.0 の5・6章

### 4.1 生成列と UNIQUE

| テーブル | 生成列 | 計算 | UNIQUE の名前 |
|---|---|---|---|
| users | email_active | 削除されていなければ email | uk_users_email_active |
| roles | name_active | 削除されていなければ name | uk_roles_name_active |
| categories | name_active | 削除されていなければ name | uk_categories_name_active |
| categories | initial_active | 削除されていなければ initial | uk_categories_initial_active |
| equipment | management_no_active | 削除されていなければ management_no | uk_equipment_management_no_active |
| loans | active_equipment_id | 返却日が空で、取り消されていなければ equipment_id（二重貸出の防止） | uk_loans_active_equipment_id |

生成列ではない UNIQUE：password_tokens.token_hash（uk_password_tokens_token_hash）、reminder_runs.target_month（uk_reminder_runs_target_month）。

照合順序が大文字・小文字、ひらがな・カタカナ、「ハ」「バ」「パ」を区別するので、「PC」と「pc」は別の名前として登録できる（データ設計 2章）。

### 4.2 外部キー（ほかのテーブルの行を指す列）

データ設計 5章で「〜を指す」と書いた列に、外部キーを付ける。指す先の行がない値は入らない。指す先の行を物理的に消すこともできない（論理削除なので、消すことはない）。

| テーブル.列 | 指す先 | 名前 |
|---|---|---|
| users.role_id | roles.id | fk_users_role_id |
| role_permissions.role_id | roles.id | fk_role_permissions_role_id |
| role_permissions.permission_code | permissions.code | fk_role_permissions_permission_code |
| equipment.category_id | categories.id | fk_equipment_category_id |
| loans.equipment_id | equipment.id | fk_loans_equipment_id |
| loans.user_id | users.id | fk_loans_user_id |
| password_tokens.user_id | users.id | fk_password_tokens_user_id |
| reminder_logs.run_id | reminder_runs.id | fk_reminder_logs_run_id |
| reminder_logs.user_id | users.id | fk_reminder_logs_user_id |
| reminder_log_items.log_id | reminder_logs.id | fk_reminder_log_items_log_id |
| reminder_log_items.equipment_id | equipment.id | fk_reminder_log_items_equipment_id |

記録用の列（created_by・updated_by）には外部キーを付けない（7章の No.3）。

### 4.3 CHECK 制約（入ってよい値の決まり）

| 名前 | テーブル | 決まり | 写したもと |
|---|---|---|---|
| ck_equipment_status | equipment | status は MANAGED・DISPOSED・MISSING のどれか | データ設計 5.6 |
| ck_equipment_disposed_on | equipment | disposed_on は、status が DISPOSED のときだけ入る（ほかの status では空） | データ設計 5.6 |
| ck_loans_due_on | loans | due_on は、空か、lent_on 以降 | データ設計 5.7 |
| ck_loans_returned_on | loans | returned_on は、空か、lent_on 以降 | データ設計 5.7 |

データ設計に CHECK と書いていない決まり（例：種別の頭文字は英大文字、既定の権限は1行だけ、催促の結果は SUCCESS か FAILURE）は、CHECK にせず、それぞれの機能のプログラムで守る（7章の No.4）。

### 4.4 索引

データ設計 6章の索引を付ける。

| 名前 | テーブル | 列 |
|---|---|---|
| idx_equipment_status_last_confirmed_on | equipment | status, last_confirmed_on |
| idx_equipment_category_id | equipment | category_id |
| idx_loans_equipment_id_lent_on | loans | equipment_id, lent_on |
| idx_loans_user_id_returned_on | loans | user_id, returned_on |
| idx_password_tokens_user_id_created_at | password_tokens | user_id, created_at |
| idx_reminder_logs_run_id | reminder_logs | run_id |
| idx_users_role_id | users | role_id |

外部キーの列で、上の索引がないもの（role_permissions.permission_code、reminder_logs.user_id、reminder_log_items.equipment_id）には、MySQL が外部キーのための索引を自動で作る。

### 4.5 そのほか

- persistent_logins は、Spring Security の決めた形（列名・型）にそろえ、username だけ 254 文字にする（データ設計 5.9）。外部キーは付けない（Spring Security がメールアドレスで読み書きするため）。
- 初めの値（DEFAULT）を付けるのは、version と users.failed_login_count（どちらも 0）だけ（7章の No.2）。

## 5. 最初のデータ

写したもと：データ設計.md v1.0 の5.3・7章

| テーブル | 入れるデータ |
|---|---|
| permissions | 5.3 の18行。sort_order は 5.3 の表の上から 1〜18 |
| roles | id=1「総務」（is_default＝false）、id=2「一般社員」（is_default＝true） |
| role_permissions | 総務：18 個すべて。一般社員：LOAN_SELF・CONFIRM_SELF |
| categories | id=1〜6：A：PC、B：ヘッドセット、C：マウス、D：カメラ、E：モニター、F：アダプタ（頭文字：名前） |
| users | 最初の総務の担当者1人：氏名「関谷 海仁」、権限は総務（role_id=1）、パスワードは空（password_hash は NULL）、メールアドレスは設定から（下の表） |

- roles と categories は id を決めて入れる（users の role_id を、JOIN やサブクエリを使わずに書くため）。AUTO_INCREMENT は、入れた id の次（roles は 3、categories は 7）から続く。
- created_at・updated_at は、日本時間の今の日時（`CONVERT_TZ(UTC_TIMESTAMP(), '+00:00', '+09:00')`。データベースの時間帯の設定に左右されない）。created_by・updated_by は空（人がいない作業のため。データ設計 2章）。version は 0。

**最初の総務の担当者のメールアドレスの渡し方**（データ設計 7章「プログラムに書かず、環境ごとの設定で渡す」）

| 環境 | 渡し方 |
|---|---|
| 開発（各自のPC） | Server の secret.yml の `app.initial-admin-email`（Git で管理しない） |
| 本番（AWS） | 環境変数 `APP_INITIAL_ADMIN_EMAIL` |
| 自動テスト | application-test.yml の `spring.flyway.placeholders.initial_admin_email: admin@example.com`（本物のアドレスはテストのデータベースに入れない） |

1. application.yml で、`spring.flyway.placeholders.initial_admin_email` に `${app.initial-admin-email:}` を渡す。
2. V2 の SQL の `${initial_admin_email}` を、Flyway がその値に置き換える（Flyway のプレースホルダー＝SQL の中の置き換える印）。
3. SQL では `NULLIF(LOWER(TRIM('${initial_admin_email}')), '')` を email に入れる。前後の空白を除き、小文字にそろえる（データ設計 8章の決めたこと1）。
4. **当て始める前の確かめ**：common.config.InitialAdminEmailCallback（Flyway の Callback＝Flyway の決まった時点で呼ばれる部品。Spring Boot が自動で Flyway に渡す）が、Flyway が当て始める前（BEFORE_MIGRATE）に、次のように確かめる。
   - 設定があり、形が正しければ、そのまま当てる。形が正しいとは：@ を1つ含み、空白・タブ・改行・「'」「"」「\」を含まない（前後の半角スペースだけは許す。SQL の TRIM で除けるため）。設定の値は SQL の '…' の中にそのまま入るので、「'」などがあると SQL が壊れ、V2 が失敗として記録に残ってしまうため。
   - 形が正しくなく、V2 の成功がまだないなら、「最初の総務の担当者のメールアドレス（app.initial-admin-email）の形が正しくありません。…」で止める。文には設定の値を入れない（秘密のため。API設計 6章）。
   - 設定が空で、Flyway の記録に V2 の成功がまだない（初めて当てる）なら、「最初の総務の担当者のメールアドレス（app.initial-admin-email）が設定されていません。開発では secret.yml、AWS では環境変数 APP_INITIAL_ADMIN_EMAIL に設定してから起動してください（docs/データ設計.md 7章）。」で止める。何も当てないので、設定してから起動し直せば、V1 から当たる。
   - 設定が空・形が正しくなくても、V2 がすでに当たっているなら止めない（最初のデータを入れ終えたあとは、メールアドレスの設定は使わないため）。
   - Flyway の記録のテーブルの名前は SQL に入れるので、英数字と「_」だけかを確かめてから入れる。
5. 3の NULLIF は、4の確かめをすり抜けたときの最後の守り。email の NOT NULL に引っかかって V2 が失敗する（メールアドレスのない総務の担当者は作られない）。

## 6. ほかへの影響

| No. | 相手 | 内容 | 対応 |
|---|---|---|---|
| 1 | 各自の開発用のデータベース（equipment_dev） | 次にサーバーを起動したときに、V1・V2 が当たる | 起動の前に、secret.yml に `app.initial-admin-email` を書く（5章） |
| 2 | すべての機能 | テーブルと列の名前は、この SQL のとおり。mapper の XML はこれに合わせる | 列を変えるときは新しい版のファイルを足し、相手に伝える（CLAUDE.md 9章） |
| 3 | テスト | テストを始める前に、TestFlywayConfig が V1・V2 を当て直す。最初のデータ（権限・種別・総務の担当者）は、どのテストでもある状態から始まる | テストで足したデータは、テストの終わりに元に戻す（テスト方針 4章） |

## 7. 設計書にない判断

| No. | 判断 | 理由 | 外から見えるか | 人の確認 |
|---|---|---|---|---|
| 1 | 詳細設計に、各テーブルの列の表を写さない。この資料を、機能のフォルダでなく `詳細設計/テーブル.md` に置く | 列はデータ設計 5章と SQL のファイルがそのまま一覧になり、3つ目の写しを持つと食い違いのもとになるため。テーブルは機能ではなく基盤のため | いいえ | 済（2026-11-08） |
| 2 | version と failed_login_count の初めの値を 0 にした（DEFAULT 0） | データ設計に初めの値が書いていない。failed_login_count は「最初は0」（データ設計 5.1）。version は 0 から数えることにした | いいえ（version は API で返すが、値そのものに意味はない） | まだ |
| 3 | created_by・updated_by に外部キーを付けない | users 自身にもある列で、最初のデータ（人がいない）では空になるため。データ設計にも「〜を指す」と書いていない | いいえ | まだ |
| 4 | データ設計に CHECK と書いていない決まりは、CHECK にしない | 設計書に書いていない動きを足さない（CLAUDE.md 2章）。それぞれの機能の業務チェックで守る | いいえ | まだ |
| 5 | 最初の総務の担当者のメールアドレスが設定にない・形が正しくないときは、当て始める前に止め、サーバーを起動しない（V2 が当たったあとは止めない） | メールアドレスのない総務の担当者を作らないため。V2 を失敗させると Flyway の記録に失敗が残り、人が記録を消すまで起動できなくなるため、その前に止める | はい（初めて起動するときに設定を忘れると起動しない） | まだ |
| 6 | roles・categories の最初のデータは id を決めて入れる | users.role_id を、サブクエリなしで書くため | いいえ | まだ |
| 7 | 5の確かめを、common.config に置いた（InitialAdminEmailCallback） | 機能ではなく、起動のときの設定の確かめのため。common を変えるので、2人で共有する（CLAUDE.md 9章） | いいえ | 済（2026-11-08） |
| 8 | id・論理削除・version・記録用の列は、データ設計 5章の表にあるテーブルにだけ付けた（role_permissions・reminder_log_items・persistent_logins には id がない。password_tokens・reminder_runs・reminder_logs には deleted_at・version・記録用の列がない） | データ設計 2章は「どのテーブルも id を持つ（権限項目・祝日を除く）」「論理削除」「version」「記録用の列」を全テーブルの決まりとして書いているが、5章の表にはそれらの列がないテーブルがあり、食い違う。5章の表のほうが列ごとに具体的で、persistent_logins は Spring Security の決めた形のため、5章に合わせた。データ設計 2章の書き方を「5章の表に書いたテーブルは」のように直すことを提案する | いいえ | 済（2026-11-08） |
